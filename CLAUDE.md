# CLAUDE.md

Telegram-бот управления VPN на базе [Remnawave](https://remnawave.com)

./docs/platega/README.md содержит информацию по взаимодействию с платежной системой 

Бот одной сборкой поддерживает **обе** версии панели: 2.8.x (пользователь адресуется UUID)
и 3.x (пользователь адресуется числовым `id`). Версия определяется автоматически, см. пункт 22
в «Важных заметках». Документация API:

- `./docs/api-remnawave3.2.3.json` — OpenAPI 3.2.3, актуальный контракт 3.x
- `./docs/api-remnawave2.8.1.json` — OpenAPI 2.8.1, нужен пока поддерживаем 2.8.x

Используй поиск по этим файлам, но не читай их целиком (спека 3.2.3 — 1.2 МБ, контекст забьётся мгновенно).

## Архитектура (v2)

Бот работает как **пульт управления** для Remnawave API. База данных хранит только связь
`Telegram ID <-> пользователь панели` (UUID на 2.8.x, числовой `id` на 3.x, в переходный период — оба).

### Основные компоненты

- **`internal/remnawave/client.go`** — HTTP-клиент Remnawave API
- **`internal/remnawave/version.go`** — тип `APIVersion` (V2/V3/Unknown), автодетект версии панели и потокобезопасный кэш
- **`internal/remnawave/userref.go`** — `UserRef` (UUID + числовой id) и методы клиента по конкретному пользователю
- **`internal/remnawave/errors.go`** — типизированная `APIError`, `ErrUserNotFound`, `APIStatusCode`, `IsAuthError`
- **`internal/remnawave/lookup.go`** — поиск пользователя панели по Telegram ID (массив на 2.8.x, `users/stream` на 3.x) и `ResolveUserByUUID`
- **`internal/bot/userref.go`** — шов `b.userRef(telegramID)`: единственный источник `UserRef` в пакете bot
- **`internal/bot/backfill.go`** — `BackfillRemnawaveIDs`: заполнение `users.remnawave_id` при старте
- **`internal/database/migrate_users.go`** — одноразовая перестройка таблицы `users` (снятие `NOT NULL` с `remnawave_uuid`)
- **`internal/platega/client.go`** — HTTP-клиент Platega
- **`internal/callback/server.go`** — встроенный HTTP-сервер для callback и health-check
- **`internal/database/users.go`** — таблица users (`telegram_id`, `username`, `first_name`, `remnawave_uuid` nullable, `remnawave_id`, `subscription_price`, `invited_by`; `moderator_id` архивное)
- **`internal/database/invites.go`** / **`referrals.go`** — служебные и referral-инвайты, лимиты, отзыв, first-touch и статистика
- **`internal/database/payments.go`** — таблица payments и логика подтверждения/ретраев платежей
- **`internal/database/earnings.go`** — архивное чтение старых `moderator_earnings`; новые начисления не создаются
- **`internal/database/bans.go`** — таблица `banned_users` и проверки перманентных банов
- **`internal/database/notifications.go`** — таблица `notifications_sent` (защита от повторных уведомлений)
- **`internal/database/receipts.go`** — таблица `receipts` (чеки «Моего налога»): ключ `payment_id`, состояния `pending`/`created`/`canceled`/`unknown`/`rejected`, столбление права на пробитие через `ClaimReceipt`
- **`internal/moynalog/client.go`** — HTTP-клиент закрытого API кабинета самозанятого «Мой налог» (логин по ИНН/паролю, `CreateIncome`, `ListIncomes`, `CancelIncome`)
- **`internal/bot/receipt.go`** — пробитие чека после активации подписки, добивание чеков плановым проходом, сверка по метке и оповещения владельцу
- **`internal/bot/handlers.go`** — обработчики сообщений, команд и синхронизация данных пользователей
- **`internal/bot/admin.go`** — админ-панель (инвайты, просмотр кодов, бан, уведомления, статистика, режим обслуживания)
- **`internal/bot/subscription_card.go`** — карточка «Моя подписка» (сборка текста и inline-клавиатуры, перевыпуск ссылки)
- **`internal/bot/payment_handler.go`** — пользовательский flow оплаты и ручная проверка платежей
- **`internal/bot/payment.go`** — callback-активация и retry платежей
- **`internal/bot/scheduler.go`** — scheduler подписок и платежей: каждые 30 минут + первый проход при старте
- **`internal/bot/dashboard.go`** — Session Manager и движок live-дашборда мониторинга
- **`internal/bot/dashboard_render.go`** — визуализация дашборда (прогресс-бары, флаги, метрики)
- **`internal/monitoring/`** — пакет мониторинга (MetricsClient, SyncNodes, LoadIndex, Alerter)
- **`internal/render/client.go`** — HTTP-клиент render-сервиса (субтитры на видео)
- **`internal/bot/render_handler.go`** — обработчики субтитров (голосовое → видео, кружок → кружок)
- **`cmd/migrator/main.go`** — миграция активных пользователей из старой БД

## Разработка в докере

```bash

```

### Разработка и Проверка (ОБЯЗАТЕЛЬНО)

Доступные команды:
`make down` / `make up` - управление докером
`make logs` - логи

**Твои обязательные шаги перед завершением любой задачи:**

1. Написал код -> проверь форматирование: `make fmt`
2. Изменил логику -> запусти тесты: `make tests`
   Никогда не рапортуй о завершении задачи, если `make tests` или `make fmt` выдают ошибки. Исправь их сам.

В этом репозитории разрешается делать коммиты, чтобы фиксировать последовательные изменения чаще

## Правило названий коммитов

Используй формат: `<type>: <краткое описание>`

- `type` только в нижнем регистре: `feat`, `fix`, `refactor`, `chore`, `docs`, `plan`, `init`
- описание на русском, краткое, с глаголом действия
- без точки в конце

### Тип коммита определяет версию релиза

Версия при `/release` вычисляется автоматически из типов коммитов
(conventional commits), поэтому тип надо выбирать осознанно:

| Тип коммита | Влияние на версию |
|---|---|
| `feat:` | minor (`x.Y.z`) |
| `fix:` | patch (`x.y.Z`) |
| `feat!:` / `fix!:` или футер `BREAKING CHANGE:` | major (`X.y.z`) |
| `chore:` / `docs:` / `refactor:` / `plan:` / `init:` | patch |

- **Breaking change** помечается либо `!` после типа (`feat!: ...`), либо
  строкой `BREAKING CHANGE: ...` в теле/футере коммита.
- **Оговорка 0.x:** пока версия ниже `1.0.0`, breaking-коммиты двигают minor,
  а не major (стандартное поведение для нестабильных версий).
- Приоритет bump: breaking → feat → иначе patch. Любой релиз получает номер,
  даже если в диапазоне только `chore`/`docs`.

## Важные заметки

1. **Рассылка** отправляется только активным пользователям (status=ACTIVE в Remnawave)
2. **Типы инвайтов:** служебный админский — бессрочный и бесплатный; referral — ссылка на 30 суток, trial на 72 часа и snapshot цены из `DEFAULT_SUBSCRIPTION_PRICE`
3. **Платежи Platega опциональны:** без `PLATEGA_MERCHANT_ID` и `PLATEGA_SECRET` бот работает как раньше, callback-сервер не стартует, кнопки оплаты не показываются
4. **Legacy-пользователи:** при `subscription_price = NULL` кнопка оплаты скрыта; scheduler пропускает старые записи без инвайта и цены
5. **Платёжный flow:** callback обрабатывается быстро, долгие retry не держат HTTP-запрос
   открытым; при сбое активации платёж переходит в `confirmed_not_activated`, а scheduler
   повторяет активацию без перезаписи исходного `confirmed_at`.
   **Переиспользуемый pending закрывать нельзя.** В `createPaymentForProvider`
   (`internal/bot/payment.go`) висящий pending того же провайдера без сохранённого
   `confirmation_url` (прошлый вызов кассы сорвался, не дойдя до записи ссылки)
   переиспользуется вместе с ключом идемпотентности — касса вернёт по нему тот же платёж.
   Раньше эта ветка проваливалась дальше без `else` и помечала свою же запись `expired`,
   а ссылку по ней всё равно выдавала: пользователь платил по локально закрытому платежу,
   подтверждение отвергалось как неактуальное — деньги приняты, услуга не оказана.
   `expired` ставится только платежу **другого** провайдера, который мы действительно бросаем.
   **Воскрешение платежа — только по ответу API провайдера.**
   `handleConfirmedWithNotification` принимает третий параметр `providerVerified`;
   входов три: `handleConfirmed` (тело callback Platega — `false`),
   `handleConfirmedFromProviderState` (вебхук ЮKassa после `GetPayment` и
   `verifyYooKassaPayment` — `true`), `handleConfirmedSilently` (ручная проверка через
   API — `true`). Из статусов `revivablePaymentStatuses` = {`expired`, `canceled`} платёж
   возвращается к жизни, если оплату подтвердил сверенный ответ провайдера: тело вебхука
   не авторитетно и воскрешать по нему нечего, а ответ API, сверенный с неизменной локальной
   записью, — единственный источник, которому можно доверить выдачу подписки. `chargebacked`
   (деньги уже вернули) и `confirmed_activation_failed` (активация признана невозможной,
   разбор ручной) не воскрешаются намеренно. Молчания нет ни в одном исходе: не смогли
   принять — `reportIgnoredPaymentConfirmation`, приняли по ответу провайдера —
   `reportRevivedPayment`, оба дедуплицируются по `payment_id` (`ignoredConfirmationReported`
   / `revivedPaymentReported` в `Bot`, `internal/bot/handlers.go`). Дедупликация обязательна,
   а сообщение — тем более: вебхуку мы отвечаем успехом, повторной доставки, которая
   напомнила бы о проблеме, не будет, и раньше на этом месте оставался только `slog.Warn`,
   который никто не читает.
   **Повторы запросов к кассе** (`internal/yookassa/client.go`): `maxAttempts` = 3,
   `defaultAttemptTimeout` = 15 с на попытку через `context`, `defaultRetryBackoff` = 1 с
   с линейным ростом. Повторяются транспортные ошибки (с «TLS handshake timeout» до
   `api.yookassa.ru` и началась потеря платежа) и 5xx; 4xx (401/400/404) не повторяются —
   ответ будет тем же. Повтор `POST /v3/payments` безопасен из-за ключа идемпотентности:
   касса вернёт тот же платёж, а не создаст второй, `GET` идемпотентен сам. Суммарный бюджет
   повторов намеренно уложен в `WriteTimeout` = 65 с вебхук-сервера
   (`internal/callback/server.go`): серия, вылезшая за него, обернулась бы для кассы обрывом
   вместо ответа. `SetRetryBackoff` существует только для тестов, `doPayment` разбит на
   `sendOnce` + `parsePayment`
6. **Плановый scheduler:** стартует сразу при запуске и далее работает каждые 30 минут; обрабатывает pending/confirmed_not_activated, уведомления, disable и grace kick, а **последним** шагом добивает непробитые чеки «Моего налога». Шаг чеков объявлен через `defer` в начале прохода, но выполняется в конце: поход в ФНС долгий, и уведомления с автокиками ждать его не должны, а `defer` нужен потому, что шаги между ним и концом функции умеют выходить раньше по ошибке Remnawave — от неё чеки не зависят
7. **Maintenance mode:** скрывает оплату и блокирует disable/автокики, но остальная функциональность бота продолжает работать
8. **Бан и автокик различаются:** бан пишет в `banned_users` (перманентно), автокик бан не ставит (пользователь может вернуться по новому инвайту)
9. **Сброс трафика** — счётчик `usedTrafficBytes` автоматически сбрасывается Remnawave 1-го числа при стратегии `MONTH`
10. **Сквады** опциональны — если пользователи не видят серверы, создайте internal squads в панели и добавьте UUID в `REMNAWAVE_DEFAULT_SQUAD_UUIDS`
11. **Трафик** — без лимита для оплаченных и админских пользователей (`trafficLimitBytes=0`); для триала лимит задаётся через `TRIAL_TRAFFIC_LIMIT_GB`
12. **Актуализация данных** — при каждом /start бот обновляет username и first_name в БД и синхронизирует username с Remnawave
13. **Отзыв кодов** — автор или админ может мягко отозвать только активный неиспользованный referral-код; строки и история не удаляются
14. **Субтитры** — опционально, требует запущенный render-сервис. Голосовое → видео с субтитрами, кружок → кружок с субтитрами
15. **Управление устройствами** — пользователь заходит в него inline-кнопкой
    «📱 Мои устройства» прямо из карточки «👤 Моя подписка»: можно посмотреть подключённые
    HWID-устройства, удалить одно или сбросить все (см. `internal/bot/devices.go`),
    API — `GetUserHwidDevices`/`DeleteUserHwidDevice`/`DeleteAllUserHwidDevices`.
    Экран устройств **редактирует** сообщение карточки, поэтому «🔙 Назад» (callback
    `cbSubCard`) возвращает карточку на место, а не удаляет сообщение. Отдельного
    reply-подменю подписки больше нет — уровень навигации схлопнут.
16. **Багрепорт** — зарегистрированный пользователь по кнопке «🛠 Сообщить о проблеме»
    в главном меню выбирает один или несколько серверов (мультивыбор: inline-тогглы с
    галочками ✅ + кнопка «Готово»; в списке только включённые хосты `isDisabled=false`,
    в т.ч. скрытые) и категорию проблемы, опционально пишет комментарий. Бот шлёт
    структурированный репорт админу в личку (TG ID, имя, статус подписки, список серверов,
    категория, текст). Без таблиц БД: сессия и кулдаун (10 минут на пользователя) хранятся
    in-memory. Если хостов нет — шаг выбора сервера пропускается. См. `internal/bot/bug_report.go`.
17. **Ручное продление подписки админом** — в карточке пользователя (админ-панель,
    «🔍 Инфо о пользователе») доступна inline-кнопка «➕ Продлить на месяц».
    Продление чисто техническое: **не создаёт** запись в `payments`. Меняется только
    Remnawave: `EnableUser` двигает
    `expireAt` (+1 месяц к текущей дате, если подписка `ACTIVE` или `LIMITED` и не
    истекла, иначе от текущего момента), ставит `Status=ACTIVE`, снимает лимит трафика.
    Статус `LIMITED` (исчерпан лимит трафика триала, но срок ещё не истёк) учитывается
    наравне с `ACTIVE` — иначе триальный пользователь с исчерпанным трафиком терял бы
    остаток дней при ручном продлении. Кнопка скрыта для безлимитных подписок
    (`expireAt.Year >= 2099`). Логика расчёта даты вынесена в чистую функцию
    `nextMonthExpireAt`, переиспользуемую обычной оплатой в `activateSubscription`.
    Защита от дабл-клика двухуровневая: `getPaymentMutex` сериализует конкурентные
    вызовы по telegram_id (общий с платёжным callback), а поле `adminExtendCooldown
    sync.Map` в `Bot` (telegram_id → время последнего успешного продления) дедуплицирует
    повторные подтверждения — если confirm-callback приходит повторно в течение
    `adminExtendCooldownWindow` (10 секунд) после успешного продления, `EnableUser`
    повторно не вызывается, админ получает алерт «Подписка уже продлена, повторное
    нажатие проигнорировано». Само продление вынесено в `applyAdminExtend(targetID
    int64) (time.Time, error)` — критическая секция `getPaymentMutex` держит внутри
    себя только чтение/запись Remnawave-состояния и кулдаун-проверку; отправка
    уведомления пользователю и ответ админу (`c.Edit`/`c.Respond`) выполняются уже
    после разблокировки мьютекса в `handleAdminExtendConfirm`, чтобы не задерживать
    параллельный платёжный callback на время похода в Telegram Bot API. Типизированные
    ошибки (`errAdminExtendCooldown`, `errAdminExtendUserNotFound`,
    `errAdminExtendLoadFailed`, `errAdminExtendEnableFailed`) маппятся в текст алерта
    функцией `adminExtendErrorAlert`. Текст уведомления пользователю строит чистая
    функция `extendedSubscriptionMessage(newExpireAt time.Time) string` — без побочных
    сетевых вызовов, принимает уже посчитанную дату параметром. Реализация —
    `internal/bot/admin_extend.go` (хендлеры
    `handleAdminExtendMonth`/`handleAdminExtendConfirm`/`handleAdminExtendCancel`),
    клавиатуры — `internal/bot/keyboards.go` (`AdminUserInfoKeyboard`, `AdminExtendConfirmKeyboard`).
18. **Общие приглашения** — раздел доступен всем зарегистрированным пользователям,
    но новые referral-ссылки создают только пользователи с действующей оплаченной,
    `legacy_paid_migrated` или бессрочной подпиской. Лимиты: 3 активных и 15 созданий
    за скользящие 24 часа. Ссылка живёт 30 суток, даёт trial на 72 часа и сохраняет
    snapshot `DEFAULT_SUBSCRIPTION_PRICE`. Автор и админ могут мягко отозвать только
    активную неиспользованную ссылку. `users.invited_by` хранит первого пригласившего;
    moderator-поля и `moderator_earnings` остаются архивом, новые выплаты не начисляются.
19. **Страница подписки — единственный источник инструкций.** Раздела «📚 Инструкции»
    в боте больше нет (удалены экраны iOS/Android/ПК, `InstructionsKeyboard` и их тексты):
    приложения под платформу и подключение в один тап живут на subscription page
    Remnawave и настраиваются в панели, без релиза бота. Главное меню пользователя:
    `[👤 Моя подписка]`, `[💳 Оплатить/Продлить | 📡 Серверы]`, `[ℹ️ Информация]`,
    `[🛠 Сообщить о проблеме]`, `[🎟 Приглашения]`. Карточка «👤 Моя подписка»
    самодостаточна — одно сообщение со статусом, ссылкой в `<code>` (не кликабельная,
    тап копирует) и inline-клавиатурой `SubscriptionCardKeyboard`: «🔗 Подключить
    устройство» (URL-кнопка на `subscriptionUrl`), «📱 Мои устройства», «🔄 Перевыпустить
    ссылку». Кнопки подключения и перевыпуска следуют за ссылкой — предикат
    `SubscriptionLinkVisible` (есть у активной и бессрочной подписки, нет в grace-периоде
    и при `LIMITED`); «Мои устройства» доступны любому зарегистрированному. URL-кнопка
    дополнительно проходит `isValidSubscriptionURL` — битый URL Telegram отвергает
    вместе со всем сообщением. После регистрации бот шлёт **два** сообщения: приветствие
    с reply-меню и отдельное `MsgConnectHint` с inline-кнопкой подключения и ссылкой
    (Telegram не допускает reply- и inline-разметку в одном сообщении).
20. **Перевыпуск ссылки подписки пользователем** — кнопка «🔄 Перевыпустить ссылку»
    в карточке ведёт на экран подтверждения с предупреждением о последствиях, далее
    `applyRevoke` (`internal/bot/subscription_card.go`): сначала
    `DeleteAllUserHwidDevices`, затем `RevokeUserSubscription`
    (`POST /api/users/{uuid}/actions/revoke`, панель сама генерирует новый `shortUuid`).
    Порядок важен: упавший сброс устройств оставляет состояние нетронутым, а обратный
    порядок дал бы новую ссылку при старых HWID-привязках — пользователь упёрся бы
    в лимит устройств. Кулдаун — `subRevokeCooldown sync.Map` в `Bot`,
    `subRevokeCooldownWindow` = 30 секунд, алерт называет остаток. Перед выполнением
    состояние подписки перечитывается и проверяется тем же `SubscriptionLinkVisible`:
    inline-кнопки живут в чате вечно, и карточка может устареть (grace, исчерпанный
    трафик триала). Если ответ панели потерялся (таймаут), бот перечитывает пользователя
    и сравнивает `subscriptionUrl`: сменилась — успех, не сменилась — честная ошибка,
    перечитать не удалось — «состояние ссылки неизвестно». Критическая секция общая
    с платежами (`getPaymentMutex`). Типизированные ошибки маппятся в текст алерта
    функцией `revokeErrorAlert`.
21. **Автопробитие чеков в «Мой налог»** — интеграция включается наличием
    `MOYNALOG_INN` и `MOYNALOG_PASSWORD` (как Platega и ЮKassa); без них бот работает
    как прежде. Клиент — `internal/moynalog/client.go`: логин по требованию под
    мьютексом, токен живёт только в памяти и на диск не пишется; на 401 — перелогин
    и ровно один повтор запроса, второй 401 подряд — ошибка авторизации.
    Идентификатор устройства вычисляется детерминированно из ИНН, чтобы не плодить
    устройства в кабинете при каждом перезапуске. Перечня кодов ошибок ФНС не
    существует, поэтому ответы разбираются по HTTP-статусу: 400/403/404 — не
    ретраить, 401 — перелогин, 500 и транспортные — ретраить, нечитаемый ответ —
    состояние «неизвестно». У ошибки клиента есть стадия (`Error.Stage`): обрыв
    связи **на логине** не делает судьбу чека неизвестной — `/income` не уходил,
    чека нет, это обычный ретрай; неоднозначность начинается только с обрыва на
    самом `/income`. `ListIncomes` при полной странице (`>= incomesPageLimit`, 100)
    возвращает `KindUnknown`, а не обрезанную выборку: иначе сверка решила бы,
    что чека нет, и пробила дубль. Время операции переводится из UTC в московское явным
    прибавлением трёх часов и явным суффиксом `+03:00`, без опоры на `TZ` контейнера.
    Хранение — таблица `receipts` (`internal/database/receipts.go`, миграция в
    `internal/database/db.go`) с ключом `payment_id`: связь с платежом 1:1 — это
    физический барьер против второго чека. Право на пробитие столбится **до**
    обращения к ФНС (`ClaimReceipt`, `INSERT ON CONFLICT DO NOTHING`); мьютексы
    по платежу намеренно не удаляются из `sync.Map` — удаление вернуло бы окно
    на дубль чека. Состояние `rejected` **терминальное**: туда уходит чек,
    который ФНС отвергла (400/403/404) на пути создания, `PaymentsNeedingReceipt`
    его не выбирает, повторов больше нет, разбор — руками. Со сверки (`unknown`)
    в `rejected` не уводим: там судьба уже созданного чека неизвестна, и закрыть
    его как отвергнутый — потерять чек из виду. Если чек пробит, но
    `MarkReceiptCreated` не сохранился (база заблокирована и т.п.), запись
    уводится в `unknown`, а не остаётся `pending`: иначе плановый проход пробил бы
    второй чек, а так сверка по метке найдёт свой чек и запишет uuid. Миграция
    засевает 13 чеков, пробитых владельцем вручную 6 августа 2026, — только при
    точном совпадении платежа (id, сумма, момент подтверждения), чтобы на чужой базе
    это был no-op. Пробитие (`internal/bot/receipt.go`) запускается сразу после
    активации подписки в отдельной горутине, вне мьютекса платежа и вне ответа
    вебхуку: недоступность ФНС никогда не задерживает ответ провайдеру и не
    превращается в неоплаченную услугу у клиента. После `Stop()` новые пробития
    не начинаются (`beginReceipt`/`stopReceipts` под `RWMutex` — закрыта гонка
    `sync.WaitGroup` Add/Wait); пробития планового прохода считаются тем же
    счётчиком, поэтому `Stop` дожидается и их. Наименование услуги — база из
    `MOYNALOG_SERVICE_NAME` плюс случайная метка из 6 символов в скобках. Сумма чека —
    **полная** сумма платежа: комиссия провайдера налоговую базу при НПД не уменьшает.
    Покупатель — физлицо без имени и телефона. Платежи Platega в «Мой налог» не
    вносятся молча — это осознанное решение владельца, а не упущение; тестовые платежи
    админа пробиваются наравне с обычными. Плановый 30-минутный проход scheduler
    (последний шаг в `internal/bot/scheduler.go`) добивает подтверждённые платежи ЮKassa без
    чека и чеки в состояниях `pending`/`unknown`; повторы бесконечные, сбой шага не
    срывает остальные шаги прохода, а одновременная работа платёжного пути и прохода
    даёт ровно один чек. У шага есть бюджет времени `receiptsPassBudget` = 5 минут:
    поход в ФНС стоит до минуты на платёж, и накопившаяся очередь иначе съела бы
    тики планировщика целиком — что не успели, добирается следующим проходом.
    Ошибка авторизации прерывает **весь** проход по чекам (флаг
    `receiptAuthBlocked`, сбрасывается в начале каждого прохода): пароль не
    платёжеспецифичен, и продолжение прохода делало бы по два неудачных входа на
    каждый платёж — прямая дорога к блокировке кабинета; следующий проход после
    исправления пароля работает как обычно. Если ответ ФНС потерялся (`unknown`), бот ищет свой чек в
    списке доходов за сутки вокруг времени операции по вхождению метки: одно
    совпадение — записываем uuid, ноль — пробиваем заново, больше одного — состояние
    не меняем и шлём владельцу алерт. Оповещения разделены: ошибка авторизации и
    «неверный запрос» (400/403/404) — сообщение сразу с текстом от ФНС; недоступность
    ФНС и транспортные ошибки — молча; чек не пробит больше суток — сообщение с
    платежом, датой и текстом последней ошибки; сводка раз в сутки, пока есть
    непробитые; когда непробитых нет — сообщений нет вообще. Сообщение об
    отвергнутом чеке помечается **в базе** (`receipt_rejected:<payment_id>`), а не
    в памяти: отвергнутый чек больше не появится ни в проходе, ни в сводке,
    поэтому единственное сообщение о нём обязано пережить перезапуск. По той же
    причине `ClearNotifications` (`internal/database/notifications.go`) не стирает
    маркеры, начинающиеся на `receipt` (`receipts_summary`, `receipt_stuck:`,
    `receipt_rejected:`, `receipts_integration_disabled`): владелец — тоже
    пользователь бота и платит тестовыми платежами, а раньше любая его оплата
    стирала память о застрявших чеках и обнуляла суточное окно сводки.
    Если интеграция выключена,
    а подтверждённые платежи без чеков есть — WARN в лог и разовое сообщение владельцу.
    В `docker-compose.yml` **обязательны** явные DNS (8.8.8.8 и 77.88.8.8): резолвер
    Hetzner (185.12.64.1/2) и Cloudflare отдают SERVFAIL на `lknpd.nalog.ru`, а
    Google/Quad9/OpenDNS/AdGuard/Яндекс резолвят (213.24.64.181). Без этой правки
    интеграция не заработает, а симптом выглядит как отказ ФНС.
    Заодно вебхук ЮKassa перестал молча проглатывать события, которые не смог
    сопоставить с платежом: они логируются и уходят сообщением владельцу (ответ вебхуку
    остаётся успешным, повторные доставки одного события не спамят). Аннулирование чека
    при возврате в эту работу не входит.
22. **Поддержка Remnawave 2.8.x и 3.x одной сборкой.** В 3.x у пользователя панели
    больше нет UUID: колонка `uuid` физически удалена из базы панели вместе с индексом,
    а все маршруты и тела переведены на числовой `id` (та же колонка, что 2.8.x уже
    отдаёт в API, — значение переживает апгрейд без изменений). Обновление панели и
    обновление бота — два независимых действия владельца, между ними неизбежен зазор,
    поэтому цель не «переписать под 3.x», а одна сборка, работающая до и после апгрейда
    без правки конфигурации.
    **Версия панели — только автодетект**, переменной окружения нет: `GET /api/system/metadata`
    → `response.version`, мажор ≥3 → контракт 3.x, мажор ≥4 → тоже 3.x плюс WARN «панель
    новее известной боту». Если `metadata` закрыта scope-ом `system` и отдаёт 403, работает
    запасная проба поведения: `GET /api/users/<нулевой uuid>` — 404 значит 2.8.x (валидный
    uuid, пользователя нет), 400 значит 3.x (не число). Без запасного пути «только
    автодетект» превратился бы в «бот не работает вообще» на урезанном токене. Кэш версии
    под `RWMutex`, конкурентные детекты схлопываются в один запрос (`detectMu` + повторная
    проверка кэша) — иначе после апгрейда десяток параллельных вызовов устроил бы шторм
    из `metadata`. `SetAPIVersion` существует только для тестов. Нулевым шагом планового
    30-минутного прохода scheduler идёт `RefreshAPIVersion`: апгрейд панели замечается
    даже без пользовательской активности.
    **Ре-детект по 400, а не по 404.** `doUserRequest` при 400 один раз перечитывает
    версию и повторяет запрос. 404 в триггер намеренно не входит: это штатное
    «пользователя нет в панели» (автокик получает его регулярно), каждый такой случай
    стоил бы лишнего `metadata` плюс повтора, а повторять неидемпотентные `PATCH`/`DELETE`
    — ровно то, чего надо избегать. 400 однозначен: «идентификатор не того типа», и он
    приходит в обе стороны (uuid на 3.x и число на 2.8.x одинаково не проходят валидацию).
    **`UserRef{UUID string; ID int64}`** (`internal/remnawave/userref.go`) — единая ссылка
    на пользователя панели; её принимают все методы по пользователю (`GetUser`,
    `UpdateUser`, `UpdateUsername`, `DeleteUser`, `EnableUser`, `DisableUser`,
    `RevokeUserSubscription`, `GetUserHwidDevices`, `GetUserHwidDevicesCount`,
    `DeleteUserHwidDevice`, `DeleteAllUserHwidDevices`). Причина выбора: различий между
    версиями шесть и они мелкие (идентификатор в пути, поле `uuid`/`id` в теле `PATCH`,
    `userUuid`/`userId` в двух телах HWID, способ поиска по Telegram ID, разбор `id`);
    интерфейс с двумя реализациями удвоил бы клиент и тесты ради шести `if`-ов, а
    выпиливание v2 через год — удаление тех же шести веток. `User.Ref()` отдаёт ссылку
    прямо из ответа панели — это убирает класс ошибок «взяли `remUser.UUID`, а на 3.x он
    пуст». Публичное `UpdateUserRequest.UUID` убрано: идентификатор в тело подставляет
    сам клиент, иначе вызывающая сторона продолжила бы класть пустой UUID и получать 400.
    Мёртвый `ResetUserTraffic` удалён. Ошибки типизированы (`internal/remnawave/errors.go`):
    `APIError{StatusCode, ErrorCode, Message, Body}`, `errors.Is(err, ErrUserNotFound)` для
    404, `IsAuthError` для 401/403; сравнения текста ошибки с «API error 404» в
    `isAutoKickNotFoundError`/`isRemnawaveNotFound` заменены на `errors.Is`.
    **Шов `b.userRef(telegramID)`** (`internal/bot/userref.go`) — единственный источник
    `UserRef` в пакете bot; правило жёсткое: никакой код не собирает ссылку из полей
    `database.User` руками, иначе ленивое восстановление окажется реализованным в одном
    месте из тридцати. На 3.x при пустом `remnawave_id` ссылка восстанавливается лениво
    поиском по `telegram_id` и сразу пишется в БД. Если по Telegram ID нашлось больше
    одного пользователя панели, связку **не** пишем — логируем и шлём алерт владельцу:
    молча выбрать первого значит с некоторой вероятностью привязать чужой аккаунт к
    платежу. Рядом — `remnawaveUser`, `deleteRemnawaveUser`, `resolveUserRef` (заменил
    `resolveUserUUID`), `schedulerUserRef` (доливка связки в плановом проходе) и
    `reportPanelAuthError` (401/403 — сообщение владельцу, дедуплицируется до исчезновения
    проблемы: у API-токенов панели есть срок, и молча деградировать бот не должен).
    **Поиск по Telegram ID починен заодно.** На 2.8.x `by-telegram-id` отдаёт **массив**, а
    клиент декодировал его в объект — метод всегда возвращал ошибку на живой панели, из-за
    чего шесть веток UX были мертвы (блокировка раннего продления, grace-экран, текст
    кнопки оплаты, дата окончания в сообщении об оплате, сверка при ручной проверке
    платежа, статус подписки в багрепорте). На 3.x маршрут удалён, замена —
    `GET /api/users/stream?telegramId=…&size=2` (второй элемент нужен только чтобы
    заметить дубликат). Результат всегда дофильтровывается точным сравнением `telegramId`:
    в OpenAPI точность фильтра не выражена, а `GET /api/users?filters=` в панели вообще
    реализован как `LIKE '%value%'`. Отсутствие пользователя — `(nil, nil)`, а не ошибка;
    reconcile при старте (`internal/bot/startup.go`) на это рассчитывает явной ветвью
    «освободить инвайт» — раньше на этом месте была бы паника при старте.
    **БД:** добавлена `users.remnawave_id INTEGER` и частичный уникальный индекс
    `idx_users_remnawave_id ... WHERE remnawave_id IS NOT NULL`; `remnawave_uuid` стал
    nullable — у пользователя, созданного уже на 3.x, UUID нет вовсе. SQLite не снимает
    `NOT NULL` через `ALTER`, поэтому `internal/database/migrate_users.go` делает
    одноразовую перестройку таблицы **целиком в одной транзакции** (`DROP TABLE IF EXISTS
    users_new` от прерванной попытки, создание, поимённый `INSERT…SELECT` девяти колонок,
    `DROP`, `RENAME`, сверка `COUNT(*)` до и после; `PRAGMA foreign_keys` off/on — вне
    транзакции, как требует SQLite). Транзакция обязательна: падение процесса между
    `DROP TABLE users` и `RENAME` оставило бы базу без таблицы, а следующий старт создал
    бы её пустой через `CREATE TABLE IF NOT EXISTS` — тихая полная потеря пользователей.
    Колонки перечисляются поимённо, потому что физический порядок колонок в чужой базе
    зависит от того, какие `ALTER` когда отработали. `database.User.RemnawaveUUID` стал
    `*string` (иначе `Scan` вернул бы `converting NULL to string is unsupported` для
    каждого, кто зарегистрировался после апгрейда), добавлен `RemnawaveID *int64`,
    `CreateUser`/`CreateUserWithInviter` принимают указатели. **Пустой UUID пишется как
    `NULL`, а не пустая строка**: колонка `UNIQUE`, SQLite допускает сколько угодно `NULL`,
    но не две пустые строки — иначе регистрация на 3.x работала бы ровно один раз.
    Новые методы: `GetUserByRemnawaveID`, `SetRemnawaveID`, `UsersMissingRemnawaveID`;
    `Subscriber` в `invites.go` получил `RemnawaveID`.
    **Backfill** (`internal/bot/backfill.go`) запускается из `cmd/bot/main.go` сразу после
    детекта версии и **до** reconcile (reconcile сам ходит в панель): на 2.8.x — один
    `GET /api/users` на всю базу с сопоставлением по UUID плюс точечный `resolve` для
    отставших, синхронно; на 3.x — поиск по `telegram_id` с паузой 100 мс на пользователя,
    в фоне (дороже: запрос на пользователя вместо запроса на базу). Кого панель не знает
    вовсе — остаётся `NULL` и перечисляется в логе поимённо: это кандидаты на ручной
    разбор, а не повод ронять старт.
    **Порядок выката обязателен**, потому что апгрейд панели удаляет UUID безвозвратно
    (`DROP COLUMN uuid` в Prisma-миграции) и после этого сопоставить нашу запись с
    пользователем панели по UUID невозможно **никогда**: 1) снять копию `bot.db`
    (перестройка `users` необратима); 2) выкатить бота на панели 2.8.x; 3) убедиться по
    логам, что backfill прошёл и строк с `remnawave_id IS NULL` не осталось; 4) обновить
    панель до 3.x (дополнительных переменных окружения релизная 3.x не требует);
    5) проверить по логам, что бот подхватил смену версии, и прогнать сквозной сценарий
    (карточка подписки → устройства). Бесшовного отката панели на 2.8.x не существует:
    Prisma-миграции назад не откатываются, откат возможен только восстановлением дампа
    Postgres. `remnawave_uuid` остаётся заполненным у всех, созданных на 2.8.x, как
    страховка на этот случай; удаление колонки — отдельная работа, не раньше чем через
    несколько релизов после окончательного переезда на 3.x.

## Мониторинг нод

### Архитектура

- **VictoriaMetrics** — база метрик (порт 8428)
- **vmagent** — скрейпит Node Exporter на нодах
- **Бот** — генерирует `targets.json`, читает метрики через PromQL

### Конвенция тегов

На нодах в Remnawave задаётся тег `bw:<число>` для указания bandwidth в Mbps.
Пример: `bw:1000` = 1 Gbit. Дефолт: 1000 Mbps.

### Алерты

Бот отправляет админу алерты при:

- Нода OFFLINE (Node Exporter не отвечает)
- Load Index > 80% (перегрузка)

### Установка Node Exporter на ноду

```bash
bash scripts/install-node-exporter.sh <IP_СЕРВЕРА_БОТА>
```
