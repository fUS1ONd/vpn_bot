# Тестовый стенд

Стенд поднимает бота с заглушкой панели Remnawave: настоящая панель не нужна.
Годится, чтобы прогнать пользовательский flow руками перед выкатом, снять
скриншоты интерфейса и проверить платёжный путь на тестовом магазине ЮKassa.

## Изоляция от прода

Стенд живёт в отдельном compose-проекте (`-p vpn-bot-test`), со своей сетью,
своими контейнерами и своей папкой данных `./data-test`. Боевые контейнеры он не
видит и не останавливает.

`docker-compose.yml` и `Dockerfile` стенд не меняет. `docker compose` сам
подхватывает только `docker-compose.yml` и `docker-compose.override.yml`, а
`docker-compose.test.yml` — нет, поэтому обычный `make up` на машине с продом
поднимает ровно прод и ничего больше.

Три условия, нарушение которых стоит дорого:

- **Свой `BOT_TOKEN`.** Отдельный бот у @BotFather. С боевым токеном стенд
  перехватит апдейты у боевого бота: Telegram отдаёт каждый апдейт одному
  получателю.
- **Тестовый магазин ЮKassa.** С боевыми ключами спишутся настоящие деньги.
  На тестовом магазине автоплатежи доступны по умолчанию, согласование не нужно.
- **Только команды стенда.** Всегда `make stand-*` или явные `-p` и `-f`. Голый
  `docker compose down` в этом каталоге остановит **боевые** контейнеры.

## Запуск

```bash
cp .env.test.example .env.test   # заполнить BOT_TOKEN, ADMIN_ID и ключи тестового магазина
make stand-up
make stand-logs
```

Остановить, стереть данные:

```bash
make stand-down    # остановить, данные сохранить
make stand-reset   # остановить и стереть базу стенда
```

Цели Makefile сами подставляют `-p vpn-bot-test -f docker-compose.test.yml
--env-file .env.test`. Если запускаете руками — подставляйте их сами, все три.

## Заглушка панели

`cmd/mockpanel` — HTTP-сервер, отвечающий на те эндпоинты Remnawave, которые
использует бот: метаданные, список и карточка пользователя, создание,
обновление, перевыпуск ссылки, HWID-устройства, ноды, хосты. Состояние держится
в памяти и умирает вместе с контейнером.

Два семейства маршрутов, и путать их нельзя:

- `/api/...` — контракт Remnawave. Заглушка обязана отвечать в нём ровно то, что
  ожидает боевой клиент, включая различия 2.8.x и 3.x. Меняя эти маршруты,
  сверяйтесь с `internal/remnawave/client.go`, а не с документацией панели:
  важно то, что бот действительно разбирает.
- `/mock/...` — пульт стенда: рычаги, которых у настоящей панели нет.

`MOCK_PANEL_VERSION` задаёт контракт, который увидит бот: `2.8.1` (пользователь
адресуется UUID) или `3.2.3` (числовым `id`). Обе ветки проверяются одним
стендом. Сама заглушка принимает **оба** способа адресации независимо от
версии — так одна и та же ручная проверка проходит на любой из них.

Запустить отдельно, без докера:

```bash
MOCK_PANEL_PORT=8081 go run ./cmd/mockpanel
```

Тесты заглушки — `go test ./cmd/mockpanel/`. Они держат контракт: формат ответа
устройств, разбор `delete`/`delete-all`, формат тела ошибки.

## Пульт стенда

Порт заглушки проброшен на `127.0.0.1:${MOCK_PANEL_PORT:-8081}`. Боту она видна
по имени сервиса внутри сети; наружу нужна только ради пульта.

### `POST /mock/user` — состояние пользователя

Находит пользователя по `telegramId` и меняет поля. Все поля необязательные,
меняется только присланное.

| Поле | Что делает |
|---|---|
| `expireInHours` | Ставит `expireAt` через N часов от «сейчас». Отрицательное — в прошлое |
| `status` | `ACTIVE`, `DISABLED`, `LIMITED`, `EXPIRED` |
| `usedTrafficGB` | Потраченный трафик |
| `devices` | Выдать N правдоподобных HWID-устройств (0 — убрать все) |

```bash
# Подписка кончается через 60 часов — окно уведомления «за 3 дня»
curl -X POST localhost:8081/mock/user -d '{"telegramId":123456,"expireInHours":60}'

# Через 12 часов — окно «за 1 день»
curl -X POST localhost:8081/mock/user -d '{"telegramId":123456,"expireInHours":12}'

# Час назад — истечение и начало grace-периода
curl -X POST localhost:8081/mock/user -d '{"telegramId":123456,"expireInHours":-1}'

# 73 часа назад — grace-кик
curl -X POST localhost:8081/mock/user -d '{"telegramId":123456,"expireInHours":-73}'

# Триал с исчерпанным трафиком: карточка покажет «Лимит трафика исчерпан»
curl -X POST localhost:8081/mock/user -d '{"telegramId":123456,"usedTrafficGB":1.5}'

# Три устройства — экран «Мои устройства» и счётчик в карточке
curl -X POST localhost:8081/mock/user -d '{"telegramId":123456,"devices":3}'
```

Срок задаётся **относительно «сейчас»**, а не датой: все окна планировщика
считаются от текущего момента, и с абсолютной датой пришлось бы каждый раз
считать руками.

### `POST /mock/fail` — отказы панели

Проваливает N ближайших запросов к `/api/` заданным статусом. Нужен, чтобы
смотреть, что видит пользователь, когда панель отвалилась.

```bash
curl -X POST localhost:8081/mock/fail -d '{"count":3,"status":500}'
curl -X POST localhost:8081/mock/fail -d '{"count":0}'   # выключить
```

Тело ошибки отдаётся в формате панели (`{message, errorCode}`) — том самом,
который разбирает `internal/remnawave/errors.go`.

Детект версии (`/api/system/metadata`) из-под отказов исключён намеренно:
провалившийся детект увёл бы стенд в состояние, которое проверять никто не
собирался, вместо экрана ошибки конкретного действия.

### `POST /mock/latency` — задержка ответов

Задерживает ответы `/api/` на указанное число миллисекунд. Нужен, чтобы увидеть
индикацию ожидания: на мгновенной заглушке «⏳ Создаю платёж…» мелькает и
исчезает.

```bash
curl -X POST localhost:8081/mock/latency -d '{"ms":3000}'
curl -X POST localhost:8081/mock/latency -d '{"ms":0}'   # выключить
```

Пульт под задержки и отказы **не** попадает: иначе включённый отказ нечем было
бы выключить.

## Как заставить планировщик сработать сразу

Плановый проход идёт раз в 30 минут, но **первый — сразу при старте**. Поэтому
после правки срока проще перезапустить контейнер бота, чем ждать:

```bash
docker compose -p vpn-bot-test -f docker-compose.test.yml restart vpn-bot-test
```

## Повторная проверка того же уведомления

Уведомления дедуплицируются таблицей `notifications_sent`: второй раз то же
самое не придёт. Самый простой способ прогнать сценарий заново — снести базу
стенда и зарегистрироваться по новому инвайту:

```bash
make stand-reset
```

Точечно, без потери регистрации:

```bash
sqlite3 data-test/bot.db "DELETE FROM notifications_sent WHERE telegram_id = 123456;"
```

## Сценарии, которым нужна правка базы бота

Часть поведения считается не от панели, а от собственных данных бота, и пультом
её не сдвинуть. Правится прямо в `data-test/bot.db`:

```bash
# Отодвинуть регистрацию в прошлое (сценарии, считающие время с момента входа)
sqlite3 data-test/bot.db "UPDATE users SET created_at = datetime('now','-6 hours') WHERE telegram_id = 123456;"

# Снять цену подписки — поведение legacy-пользователя, у которого скрыта оплата
sqlite3 data-test/bot.db "UPDATE users SET subscription_price = NULL WHERE telegram_id = 123456;"
```

## Чего на стенде нет

Знать заранее дешевле, чем упереться посреди проверки:

- **Канал сообщества.** `COMMUNITY_CHAT_ID` и `COMMUNITY_INVITE_LINK` в
  `docker-compose.test.yml` не заданы, поэтому гейта заявок и приписок про Канал
  на стенде не будет. Чтобы проверять их, нужна отдельная тестовая
  форум-супергруппа, где тестовый бот — админ.
- **Мониторинг.** VictoriaMetrics и vmagent в стенд не входят, ноды и хосты
  заглушка отдаёт пустыми: дашборд «📡 Серверы» будет пустым.
- **«Мой налог».** Чеки на стенде не пробиваются — интеграция включается только
  наличием ИНН и пароля, которых в `.env.test.example` нет намеренно.
- **Inline-режим бота.** Кнопки, использующие `switch_inline_query`, требуют
  `/setinline` у @BotFather для тестового бота.
- **Вебхуки ЮKassa** доходят до стенда только через туннель (ngrok,
  cloudflared) на `TEST_CALLBACK_PORT`. Без туннеля платёж подтверждается
  кнопкой «🔄 Проверить оплату» — она ходит в API кассы сама.
