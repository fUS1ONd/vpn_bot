# Совместимость бота с Remnawave 2.8.x и 3.x одновременно

Дата: 2026-08-13
Статус: черновик, на согласовании
Версии в работе: панель `2.8.1` (текущая у владельца) и `3.2.3` (последняя), нода `3.1.1`

## Проблема

31 июля 2026 вышла Remnawave 3.0.0 — мажорный релиз с ломающими изменениями API.
К 10 августа панель дошла до 3.2.3. Наш бот написан под контракт 2.8.x и после
обновления панели перестанет работать полностью: сломаются регистрация, оплата,
продление, автокик, устройства, перевыпуск ссылки — всё, что ходит в панель по
пользователю.

Обновление панели и обновление бота — два независимых действия владельца, и
между ними неизбежен зазор. Значит цель не «переписать под 3.x», а **одна сборка
бота, работающая и до, и после мажорного обновления панели**, без правки
конфигурации в момент апгрейда.

## Что уже сделано в рамках этой работы

- `docs/api-remnawave3.2.3.json` — OpenAPI 3.2.3 (1.2 МБ, 147 путей, 224 схемы),
  забран с `https://cdn.remna.st/docs/openapi.json`. Это тот же файл, что показывает
  `https://docs.rw/api`: бэкенд по тегу релиза генерирует спеку и пушит её в R2
  (`.github/workflows/push-openapi-specs.yml`), а docs.rw рендерит её Scalar'ом.
  Лежит рядом с `docs/api-remnawave2.8.1.json` — старая спека остаётся в репозитории,
  она нужна ровно столько, сколько мы поддерживаем 2.8.x.
- Разбор различий двух спек и релиз-нот `remnawave/backend` за 2.8.1 → 3.2.3.

Примечание: файл старой спеки называется `api-remnawave2.8.1.json`, и внутри
`info.version = 2.8.1` — версии «2.8.4» у панели не существует, последний релиз
ветки 2.x — 2.8.1 от 13 июля 2026.

## Что изменилось в API

### Главный слом: у пользователя больше нет UUID

В 3.x колонка `uuid` у пользователя удалена из базы панели («Drop user uuid, rename
user id column in database»), а все маршруты и тела переведены на числовой `id`
(«Replace all users routes to use id instead of uuid»). Ответ `GET /api/users/{userId}`
в 3.2.3 не содержит поля `uuid` вообще — есть `id: number`, `shortUuid`, `vlessUuid`.

Это ломает нашу центральную сущность: в БД мы храним `users.remnawave_uuid` и
передаём его в каждый вызов клиента.

Важно и обнадёживающе: **в 2.8.1 числовой `id` уже присутствует** в ответах
(`GET /api/users`, `GET /api/users/{uuid}`, `POST /api/users`, `POST /api/users/resolve`).
То есть мост между версиями существует: находясь ещё на 2.8.x, бот может заранее
узнать и сохранить `id` каждого пользователя.

Причём это тот же самый идентификатор, а не новый. Миграции панели
(`prisma/migrations` в `remnawave/backend`) показывают точную механику апгрейда:

```sql
-- 20260720124815_rename_column
ALTER TABLE "users" RENAME COLUMN "t_id" TO "id";
-- 20260720132335_drop_user_uuid
DROP INDEX "users_uuid_key";
ALTER TABLE "users" DROP COLUMN "uuid";
```

Два следствия, на которых держится весь план:

1. **`id` переживает апгрейд без изменения значения** — это старая колонка `t_id`,
   которую 2.8.x уже отдаёт в API. Значит `id`, собранный ботом до апгрейда,
   остаётся валидным после него.
2. **UUID уничтожается физически.** Не «перестаёт отдаваться в API», а удаляется
   из базы панели вместе с индексом. После апгрейда сопоставить нашу запись с
   пользователем панели по UUID невозможно **никогда** — только по `id`,
   `telegramId`, `username` или `shortUuid`.

Отсюда главное эксплуатационное требование: бот с поддержкой обеих версий должен
быть выкачен и отработать backfill **до** обновления панели. Порядок выката
описан ниже отдельным разделом.

### Удалённые маршруты поиска пользователя

| 2.8.1 | 3.2.3 |
|---|---|
| `GET /api/users/by-telegram-id/{telegramId}` | удалён |
| `GET /api/users/by-email/{email}` | удалён |
| `GET /api/users/by-tag/{tag}` | удалён |
| `GET /api/users/by-id/{id}` | удалён (слился с `GET /api/users/{userId}`) |
| — | `GET /api/users/stream?telegramId=…` (есть и в 2.8.1, но без фильтров) |

Замена поиска по Telegram ID в 3.x — `GET /api/users/stream?telegramId=<id>`.
Детали, без которых метод не написать:

- параметр `telegramId` объявлен **строкой** — передавать десятичное представление,
  не число;
- ответ курсорный: `{users[], nextCursor, hasMore}`, размер страницы `size`
  (по умолчанию 250, максимум 1000). Для поиска одного пользователя достаточно
  первой страницы с `size=2` — второй элемент нужен только чтобы заметить дубликат
  `telegramId`;
- в самой спеке панели типы курсора не сходятся: запрос принимает `cursor: number`,
  а ответ отдаёт `nextCursor: string`. Пагинацию по `stream` в этой работе мы не
  используем — если понадобится, поведение придётся проверять на живой панели;
- объекты пользователя в ответе полные (есть `subscriptionUrl`, `userTraffic`),
  отдельный `GET` после поиска не нужен.

По исходникам панели фильтр точный (`where telegram_id = BigInt(value)` в
`users.repository.ts`), но исходника у нас в репозитории нет и в OpenAPI это не
выражено — поэтому результат в любом случае **дофильтровывается на нашей стороне**
точным сравнением `telegramId`. То же правило действует для
`GET /api/users?filters=[{"id":"telegramId","value":"…"}]`, который для поиска
вообще **не годится**: в репозитории панели он реализован как
`CAST(telegram_id AS TEXT) LIKE '%value%'`, то есть `123` найдёт и `1234`, и `91230`.

### Пути и тела: постатейно по тем вызовам, что делает бот

| Операция | 2.8.1 | 3.2.3 |
|---|---|---|
| Создать пользователя | `POST /api/users` (201) | без изменений; в ответе `id`, нет `uuid` |
| Прочитать пользователя | `GET /api/users/{uuid}` | `GET /api/users/{userId}` (number) |
| Обновить | `PATCH /api/users`, тело с `uuid` | `PATCH /api/users`, тело с `id: number` |
| Удалить | `DELETE /api/users/{uuid}` → 200 `{isDeleted}` | `DELETE /api/users/{userId}` → **204** без тела |
| Сброс трафика | `POST /api/users/{uuid}/actions/reset-traffic`, тела нет | меняется только идентификатор |
| Перевыпуск ссылки | `POST /api/users/{uuid}/actions/revoke`, тело `{shortUuid?, revokeOnlyPasswords?}` | тело то же самое, меняется только идентификатор |
| Поиск по Telegram ID | `GET /api/users/by-telegram-id/{id}` → **массив** | `GET /api/users/stream?telegramId=` → `{users[], nextCursor, hasMore}` |
| Список всех | `GET /api/users?size=&start=` | те же параметры (`size` теперь 1…1000, по умолчанию 25) плюс новые `filters`, `filterModes`, `globalFilterMode`, `sorting` |
| Список устройств | `GET /api/hwid/devices/{userUuid}` | `GET /api/hwid/devices/{userId}` |
| Удалить устройство | `POST /api/hwid/devices/delete` `{userUuid, hwid}` | `{userId, hwid}` |
| Сбросить устройства | `POST /api/hwid/devices/delete-all` `{userUuid}` | `{userId}` |
| Ноды | `GET /api/nodes` | совместимо (добавились `id` и `ips`; `provider` был и в 2.8.1) |
| Хосты | `GET /api/hosts` | совместимо (`uuid`, `remark`, `isDisabled`, `nodes[]` на месте) |
| Версия панели | `GET /api/system/metadata` → `response.version` | без изменений |
| Резолв идентификаторов | `POST /api/users/resolve` `{uuid\|id\|shortUuid\|username}` | то же, но без `uuid` |

Важное для нас следствие: **URL-шаблоны совпадают** — меняется только тип значения
в пути и имя поля в теле. Разница между версиями локализована в шести местах:
идентификатор в пути, поле `uuid`/`id` в теле `PATCH`, поле `userUuid`/`userId`
в двух телах HWID, способ поиска по Telegram ID и разбор `id` из ответа.

### Валидация в 3.x строже

Панель переехала на zod v4, и часть полей получила регулярные выражения там, где
в 2.8.1 стояла свободная строка. Для нас значим `expireAt`: в 3.2.3 он обязан
заканчиваться на `Z` (`…T(?:[01]\d|2[0-3]):[0-5]\d(?::[0-5]\d(?:\.\d+)?)?Z`),
смещение вида `+03:00` не пройдёт валидацию. Сейчас клиент везде вызывает
`.UTC().Format(time.RFC3339)` — формат подходит, но это перестало быть делом
вкуса, и на это нужен тест: любая попытка отправить локальное время получит `400`
на 3.x и молча пройдёт на 2.8.x.

### Что осталось совместимым

- Аутентификация: `Authorization: Bearer <token>`, обёртка ответа `{"response": …}`.
- Статусы пользователя: `ACTIVE`, `DISABLED`, `LIMITED`, `EXPIRED`.
- Стратегии трафика: `NO_RESET`, `DAY`, `WEEK`, `MONTH`, `MONTH_ROLLING`.
- `subscriptionUrl`, `shortUuid`, `expireAt`, `trafficLimitBytes`, `hwidDeviceLimit`,
  `userTraffic.{usedTrafficBytes,lifetimeUsedTrafficBytes,onlineAt}`.
- Ноды и хосты — включая `tags` (наша конвенция `bw:<Mbps>`), `countryCode`,
  `isConnected`, `isDisabled`, `usersOnline`, `nodes[]` у хоста.
- Валидация username: `^[a-zA-Z0-9_-]+$`, 3–36 символов (как и раньше).

### Прочее в 3.x, чего мы не касаемся

- `ip-control` → `connections` (мы этим модулем не пользуемся).
- Замена `uuid` на `userId` прошла и по маршрутам, которых бот не вызывает:
  `/api/bandwidth-stats/users/{uuid}`, `/api/metadata/user/{uuid}`,
  `/api/subscriptions/by-uuid/{uuid}` → `/api/subscriptions/by-id/{userId}`,
  `/api/subscriptions/connection-keys/{uuid}`, `/api/users/{uuid}/accessible-nodes`,
  `/api/users/{uuid}/subscription-request-history`. Перечислено, чтобы при
  реализации не пришлось искать заново и гадать, не забыли ли что-то.
- Формат ошибок унифицирован: `{timestamp, path, message, errorCode}`; `errorCode`
  для «пользователь не найден» — `A025` в обеих версиях.
- Новое, что может пригодиться потом, но в объём не входит:
  `POST /api/users/{userId}/actions/extend` (продление на N дней — прямая замена
  нашей ручной арифметики в «➕ Продлить на месяц», но её нет в 2.8.1),
  `GET /api/system/configuration`, `GET /api/system/stats/digest`,
  `GET /api/system/stats/http`, bulk-операции по внутренним сквадам.
- Нода `3.1.1`: релизы автогенерируемые, публичного списка изменений нет. Бот с нодой
  не общается напрямую — только читает `/api/nodes` панели и метрики Node Exporter,
  поэтому обновление ноды на нас не влияет. Требование панели 3.x к версии ноды —
  вопрос эксплуатации, не кода бота.
- Требования подтвердить ломающие изменения переменной окружения в релизных 3.x
  **нет**: `I_UNDERSTAND_REST_API_BREAKING_CHANGES` жил только в dev-сборках и был
  удалён до релиза — `docker-entrypoint.sh` тега 3.2.3 такой проверки не содержит.
  Панель 3.x поднимется на существующем `.env` без дополнительных переменных, то
  есть апгрейд не защищён ничем и произойдёт ровно тогда, когда владелец обновит
  образ.

## Решение

### Один клиент, ветвление внутри

`internal/remnawave/client.go` остаётся единственной точкой входа. Клиент знает
версию API панели и сам решает, как построить путь и тело. Вызывающий код про
версию не знает ничего.

Причина выбора: различий шесть, и они мелкие. Интерфейс с двумя реализациями
удвоил бы объём клиента и тестов ради ветвления, которое умещается в шесть
`if`-ов, а выпиливание v2 через год — это удаление тех же шести веток.

```go
type APIVersion int

const (
    APIVersionUnknown APIVersion = iota
    APIVersionV2  // 2.8.x: пользователь адресуется UUID
    APIVersionV3  // 3.x:   пользователь адресуется числовым id
)

// UserRef — ссылка на пользователя панели, независимая от версии API.
// На 2.8.x значим UUID, на 3.x — ID; в переходный период известны оба.
type UserRef struct {
    UUID string
    ID   int64
}
```

Все методы клиента, работающие с конкретным пользователем, принимают `UserRef`
вместо `string`: `GetUser`, `UpdateUser`, `DeleteUser`, `EnableUser`, `DisableUser`,
`ResetUserTraffic`, `RevokeUserSubscription`, `UpdateUsername`,
`GetUserHwidDevices`, `GetUserHwidDevicesCount`, `DeleteUserHwidDevice`,
`DeleteAllUserHwidDevices`.

Сам тип и методы по конкретному пользователю живут в
`internal/remnawave/userref.go`. `ResetUserTraffic` в итоговый список не входит:
метод мёртвый и вместо переноса на `UserRef` просто удалён (см. «Инвентарь мест,
завязанных на UUID»).

Внутри — единственная развилка:

```go
func (c *Client) userPathSegment(ref UserRef) (string, error) {
    switch c.version() {
    case APIVersionV3:
        if ref.ID == 0 { return "", ErrUserRefMissingID }
        return strconv.FormatInt(ref.ID, 10), nil
    case APIVersionV2:
        if ref.UUID == "" { return "", ErrUserRefMissingUUID }
        return ref.UUID, nil
    }
    return "", ErrPanelVersionUnknown
}
```

`User` в Go получает оба поля: `UUID string` (пусто на 3.x) и `ID int64` (заполнено
в обеих версиях). Метод `func (u *User) Ref() UserRef` отдаёт ссылку для последующих
вызовов — это убирает целый класс ошибок «взяли UUID из ответа панели, а на 3.x он
пустой» (сейчас так делает `subscription_card.go`, беря `remUser.UUID`).

`ID == 0` как признак «не задан» безопасен: в 3.2.3 параметр пути объявлен
`number, minimum: 0, exclusiveMinimum: true`, то есть валидный `id` всегда ≥ 1.
Нулевой сентинел здесь — не недосмотр, а гарантия контракта.

`UpdateUserRequest.UUID` — экспортированное поле, которое сегодня заполняет
вызывающий код (`admin.go:594`). Его надо убрать из публичной структуры: идентификатор
в тело должен подставлять сам клиент из `UserRef`, иначе на 3.x вызывающая сторона
продолжит класть туда пустой UUID и получит `400`.

#### Шов для получения `UserRef` в боте

`remnawave.Client` не имеет и не должен иметь доступа к нашей БД, поэтому
восстановить недостающий `remnawave_id` он не может — это работа бота. Чтобы
не вкручивать восстановление в каждый из ~30 call-site-ов, вводится единственный
способ получить ссылку:

```go
// userRef — единственный источник UserRef в пакете bot.
// Читает связку из БД; если remnawave_id пуст, а панель 3.x — ищет пользователя
// по telegram_id через stream, сохраняет найденный id и возвращает ссылку.
func (b *Bot) userRef(telegramID int64) (remnawave.UserRef, error)
```

`resolveUserUUID` (`internal/bot/devices.go:34`, используется ещё из
`subscription_card.go:151,205`) заменяется на него. Правило простое: **никакой код
в `bot` не собирает `UserRef` вручную из полей `database.User`** — иначе ленивое
восстановление окажется реализованным в одном месте из тридцати. Для админских
сценариев, где действие идёт над чужим `telegram_id`, используется тот же хелпер.

Шов лежит в `internal/bot/userref.go`, и рядом с ним — вся обвязка, которой он
пользуется и которая пользуется им:

- `remnawaveUser` — чтение пользователя панели по Telegram ID через шов;
- `deleteRemnawaveUser` — удаление через шов;
- `resolveUserRef` — заменил прежний `resolveUserUUID`;
- `schedulerUserRef` — доливка связки в плановом проходе;
- `reportPanelAuthError` — реакция на `401`/`403` от панели: сообщение владельцу,
  **дедуплицированное до исчезновения проблемы** (повторные ошибки подряд не
  спамят, но после восстановления и новой поломки владелец узнает снова).
  У API-токенов панели есть срок, и молча деградировать бот не должен.

### Определение версии панели

Только автодетект, без переменной окружения — решение владельца.

Источник: `GET /api/system/metadata` → `response.version` (строка вида `3.2.3`).
Эндпоинт есть в обеих версиях с одинаковым полем. Мажор ≥ 3 → `APIVersionV3`,
мажор 2 → `APIVersionV2`, мажор ≥ 4 (будущее) → трактуем как V3 и пишем WARN,
что версия панели новее известной боту.

Правила работы:

1. **Старт бота.** Детект в `cmd/bot/main.go` сразу после создания клиента и
   **до** `bot.ReconcileOrphanedRegistrations` (`main.go:93`) — reconcile сам ходит
   в панель, и к этому моменту версия должна быть известна. Backfill (см. ниже)
   идёт там же, между детектом и reconcile. Успех — `INFO` с версией панели и
   выбранным контрактом. Неуспех — `WARN`, бот продолжает старт: панель может
   подняться позже, и падать из-за этого нельзя (у бота есть функции, не зависящие
   от панели, — оплата в БД, багрепорты, админка).
2. **Ленивый повтор.** Если версия неизвестна, любой вызов клиента сперва пытается
   определить её. Не удалось — вызов возвращает `ErrPanelVersionUnknown`
   (обёрнутая причина), а не шлёт запрос вслепую.
3. **Смена версии на лету.** Владелец обновит панель, не перезапуская бота. Кэш
   версии инвалидируется **только при `400`** на user-маршруте: единая обёртка
   запросов по пользователю (`doUserRequest`) при `400` один раз перечитывает
   `metadata` и повторяет исходный запрос ровно один раз с новым контрактом.
   Повторный сбой отдаётся наверх как ошибка.

   `404` в триггер намеренно не входит, хотя выглядит похоже. Во-первых, это
   штатный ответ «пользователь удалён из панели» — `scheduler.go:315` получает его
   на автокике регулярно, и каждый такой случай стоил бы лишнего запроса
   `metadata` плюс повтора `DELETE`. Во-вторых, повтор неидемпотентных запросов
   (`PATCH /api/users`, `DELETE`) — то, чего хочется избежать, а не добавить.
   `400` же однозначен: «идентификатор не того типа».

   Проверить на живой 3.2.3 до реализации: `PATCH /api/users` с телом, где есть
   `uuid` и нет `id`, действительно отвечает `400`. В OpenAPI `id` формально не
   помечен `required` (в обеих версиях `required: null`), так что рассчитывать на
   `400` без проверки нельзя — если панель отвечает `200` и молча ничего не
   меняет, механизм смены версии на лету для `PATCH` не сработает, и его придётся
   подпирать периодической сверкой (правило 4).
4. **Периодическая сверка.** Плановый проход scheduler (раз в 30 минут) **нулевым
   шагом** вызывает `RefreshAPIVersion` — то есть версия перечитывается до всех
   остальных шагов прохода. Это ловит апгрейд панели даже без пользовательской
   активности.

Опасное место, которое надо закрыть явно: при работе на 2.8.x запрос
`GET /api/users/<uuid>` после апгрейда панели вернёт `400` (uuid не число) — это
именно та ситуация, на которую рассчитан пункт 3. А вот в обратную сторону
(откат панели с 3.x на 2.8.x) запрос `GET /api/users/123` на 2.8.1 вернёт `400`:
там параметр валидируется как `z.string().uuid()` (контракт
`libs/contract/commands/users/get-user-by-uuid.command.ts` тега 2.8.1) — тоже покрыто.

Детект обязан быть потокобезопасным: версия читается из каждого вызова клиента,
а бот многопоточный (поллинг Telegram, вебхуки платежей, scheduler, горутины
чеков). Хранение — под `sync.RWMutex` либо `atomic.Value`; конкурентные попытки
детекта схлопываются в одну (`singleflight` или мьютекс на время запроса), иначе
после апгрейда панели десяток параллельных вызовов устроит шторм из `metadata`.

Реализовано это так (`internal/remnawave/version.go`): тип `APIVersion`
(`V2`/`V3`/`Unknown`), автодетект и кэш версии под `RWMutex`, а схлопывание
конкурентных детектов — отдельным мьютексом `detectMu` плюс **повторная проверка
кэша** после его захвата: тот, кто пришёл вторым, дожидается первого и забирает
уже готовый результат, не отправляя своего запроса `metadata`. Отдельный сеттер
`SetAPIVersion` существует **только для тестов** — в продовом коде версия
устанавливается исключительно детектом, переменной окружения для неё нет.

#### Запасной способ, если `metadata` недоступна

`GET /api/system/metadata` закрыт `ScopesGuard` (ресурс `system`). Токен с
урезанными scope'ами получит `403`, и «только автодетект» превратится в
«бот не работает вообще». Поэтому нужен запасной путь — проба поведения, не
зависящая ни от прав на `system`, ни от наличия данных в панели:

| Проба | 2.8.x | 3.x |
|---|---|---|
| `GET /api/users/00000000-0000-0000-0000-000000000000` | `404` (валидный uuid, пользователя нет) | `400` (не число) |
| `GET /api/users/1` | `400` (не uuid) | `404` или `200` |

Достаточно первой; вторая подтверждает вывод, когда первая ответила неожиданным
кодом. Обе не изменяют состояние панели и работают на пустой базе. Запасной путь
включается только после неудачи `metadata`, а её причина уходит в лог.

#### Ошибки авторизации

`401` на любом вызове — это протухший или отозванный токен: у API-токенов панели
есть срок (`expire_at`; токенам, созданным до 2.8.x, миграция проставила
`now() + 99999 дней`, то есть они фактически бессрочные, но новые владелец
создаёт с явным `expiresInDays`). Бот не должен молча деградировать: `401` и
`403` логируются как отдельная категория и уходят сообщением владельцу — так же,
как это сделано для ошибок авторизации «Моего налога». Токену бота нужен scope
`*` либо доступ на чтение/запись к `users`, `hwid`, `nodes`, `hosts` и на чтение
`system`.

### Хранение связки в БД

Схема `users` получает вторую колонку идентификатора. Миграция выполняется в три
шага в этом порядке, каждый идемпотентен:

```sql
-- шаг 1: в общий список alterMigrations (ошибка "duplicate column" игнорируется)
ALTER TABLE users ADD COLUMN remnawave_id INTEGER;
-- шаг 2: перестройка таблицы, только если NOT NULL ещё стоит (см. ниже)
-- шаг 3: индексы
CREATE INDEX IF NOT EXISTS idx_users_remnawave_uuid ON users(remnawave_uuid);
CREATE UNIQUE INDEX IF NOT EXISTS idx_users_remnawave_id
    ON users(remnawave_id) WHERE remnawave_id IS NOT NULL;
```

`remnawave_uuid` при этом обязан стать nullable: пользователь, созданный уже на
3.x, никакого UUID не имеет. Сейчас колонка объявлена `TEXT UNIQUE NOT NULL`, и
SQLite не умеет снимать `NOT NULL` через `ALTER` — нужна одноразовая перестройка
таблицы. Внешних ключей на `users` в схеме нет (проверено: `REFERENCES users` не
встречается), поэтому перестройка безопасна. Живёт перестройка отдельным файлом —
`internal/database/migrate_users.go`, вызывается из миграций `db.go`.

Актуальный набор колонок `users` — пять из `CREATE TABLE` и четыре, доехавшие
`ALTER`-миграциями (`internal/database/db.go`): `telegram_id`, `username`,
`remnawave_uuid`, `invited_by`, `created_at`, `first_name`, `subscription_price`,
`moderator_id`, `legacy_paid_migrated`. Перечислять их в `INSERT … SELECT` нужно
поимённо: физический порядок колонок в чужой базе зависит от того, в какой
момент какие `ALTER` отработали, и `INSERT INTO … SELECT *` там развалится.

```sql
-- выполняется один раз, только если PRAGMA table_info(users) показывает
-- notnull=1 у remnawave_uuid; целиком внутри одной транзакции
CREATE TABLE users_new (
    telegram_id          INTEGER PRIMARY KEY,
    username             TEXT,
    first_name           TEXT,
    remnawave_uuid       TEXT UNIQUE,          -- NOT NULL снят
    remnawave_id         INTEGER,              -- новый идентификатор 3.x
    subscription_price   INTEGER,
    moderator_id         INTEGER,
    invited_by           INTEGER,
    legacy_paid_migrated INTEGER NOT NULL DEFAULT 0,
    created_at           TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- remnawave_id уже добавлен шагом 1, поэтому переносится вместе с остальным
INSERT INTO users_new (telegram_id, username, first_name, remnawave_uuid,
                       remnawave_id, subscription_price, moderator_id,
                       invited_by, legacy_paid_migrated, created_at)
SELECT telegram_id, username, first_name, remnawave_uuid,
       remnawave_id, subscription_price, moderator_id,
       invited_by, legacy_paid_migrated, created_at
FROM users;

DROP TABLE users;
ALTER TABLE users_new RENAME TO users;
```

Индексы (шаг 3) пересоздаются после перестройки — `DROP TABLE` уносит их вместе
со старой таблицей.

Для базы, уже прошедшей перестройку, миграция сводится к двум идемпотентным
`CREATE INDEX IF NOT EXISTS` — проверка через `PRAGMA table_info` делает шаг
безопасным при каждом старте.

Требования к реализации, без которых миграция опасна:

- всё внутри одной транзакции, с проверкой ошибки на каждом шаге; при любой
  ошибке — откат и отказ стартовать (а не «поехали с половиной таблицы»);
- `PRAGMA foreign_keys` в `db.go` включён — на время перестройки его нужно
  выключить и вернуть обратно (SQLite требует делать это **вне** транзакции);
- количество строк до и после сверяется: `SELECT COUNT(*)` перед `DROP` и после
  `RENAME` должны совпасть, иначе откат;
- перед выкатом версии с этой миграцией снимается копия `bot.db` — это
  единственный необратимый шаг во всей работе.

Для базы, созданной с нуля уже новой версией, `CREATE TABLE IF NOT EXISTS users`
в `migrate()` правится сразу: `remnawave_uuid TEXT UNIQUE` (без `NOT NULL`) и
`remnawave_id INTEGER` — тогда перестройка не понадобится вовсе. Без этой правки
каждая свежая база создавалась бы с `NOT NULL` и тут же перестраивалась — работает,
но делает тест «свежая база» бессмысленным.

Место шага внутри `migrate()` фиксировано: после цикла `alterMigrations` (чтобы
`remnawave_id` уже существовал и переносился) и **до** создания индексов (`DROP
TABLE` уносит `idx_users_remnawave_uuid`, созданный в первом цикле, — его надо
пересоздать после `RENAME`).

Дополнительно к шагам выше: в начале — `DROP TABLE IF EXISTS users_new` (остаток
от прерванной попытки), и всё вместе внутри `BEGIN IMMEDIATE … COMMIT`. Без
транзакции падение процесса между `DROP TABLE users` и `RENAME` оставляет базу
без таблицы `users`, а следующий старт создаст её пустой через
`CREATE TABLE IF NOT EXISTS` — тихая полная потеря пользователей, худший исход
во всей работе.

#### Go-сторона: NULL нельзя прочитать в `string`

Это отдельная ловушка, из-за которой бот сломается не при апгрейде панели, а при
первой же регистрации на 3.x. Сейчас `remnawave_uuid` сканируется прямо в
`user.RemnawaveUUID string` (`internal/database/users.go:38,76,121`). Как только
в колонке появится `NULL`, `Scan` вернёт `converting NULL to string is unsupported`,
и `GetUserByTelegramID` начнёт падать для каждого такого пользователя — то есть
для всех, кто зарегистрировался после апгрейда.

Поэтому:

- `database.User.RemnawaveUUID` меняет тип на `*string` (или читается через
  `sql.NullString` и кладётся в `*string` — как уже сделано для остальных
  nullable-полей в том же файле);
- правятся все три `Scan` (`users.go:38`, `:76`, `:121`);
- `database.Subscriber.RemnawaveUUID` уже `*string` (`invites.go:42`) — там менять
  нечего, но рядом заводится `RemnawaveID` (из двух вариантов «убрать поле» и
  «завести рядом второй идентификатор» выбран второй).

Набор методов доступа после правки: `GetUserByRemnawaveID` (симметрия к
`GetUserByRemnawaveUUID`), `SetRemnawaveID` (идемпотентная запись связки) и
`UsersMissingRemnawaveID` (выборка строк с пустым `remnawave_id` — на ней стоит
backfill и плановая доливка); `CreateUser`/`CreateUserWithInviter` принимают
указатели, а `database.User` получает поле `RemnawaveID *int64`.

#### Отсутствующий UUID пишется как NULL, а не пустая строка

Симметричная ловушка на записи. `handlers.go:661`, `startup.go:60` и
`cmd/migrator/main.go:142` кладут в колонку `remnawaveUser.UUID`, который на 3.x
равен `""`. Колонка объявлена `UNIQUE`: SQLite допускает сколько угодно `NULL`, но
**не две пустые строки** — второй же зарегистрировавшийся пользователь получит
`UNIQUE constraint failed`, а `handlers.go:665` откатит его создание в панели.
Регистрация на 3.x работала бы ровно один раз.

Значит сигнатуры меняются на указатели, и правило «пустой UUID → `NULL`»
применяется в одном месте — в слое БД:

```go
func (db *DB) CreateUserWithInviter(
    telegramID int64, username, firstName string,
    remnawaveUUID *string, remnawaveID *int64,
    subscriptionPrice *int, moderatorID, invitedBy *int64,
) (*User, error)
```

Тест обязателен: две подряд регистрации без UUID должны обе пройти.

Альтернатива «писать в `remnawave_uuid` синтетическое значение вида `v3:<id>`»
рассматривалась и отвергнута: она превращает колонку в помойку, ломает смысл
`GetUserByRemnawaveUUID` и обязательно всплывёт при откате панели на 2.8.x.

### Заполнение `remnawave_id`

Backfill оформлен отдельным файлом `internal/bot/backfill.go`
(`BackfillRemnawaveIDs`) и запускается из `cmd/bot/main.go` сразу после детекта
версии и **до** reconcile — reconcile сам ходит в панель, и к этому моменту связки
должны быть на месте. На 2.8.x проход синхронный (один запрос на всю базу, ждать
недорого), на 3.x — фоновый, с паузой 100 мс между запросами: там цена прохода
совсем другая, запрос на каждого пользователя вместо одного на всю базу.

Три пути, взаимодополняющие:

1. **Backfill на 2.8.x (основной).** При старте, если бот видит панель 2.8.x и в
   БД есть строки с пустым `remnawave_id`, он делает один проход `GET /api/users`
   (пагинация уже реализована) и заполняет `remnawave_id` по совпадению `uuid`.
   Одна операция на всю базу, никаких запросов на пользователя. После этого
   апгрейд панели проходит бесшовно. Одиночные пропуски (пользователь появился
   после прохода) добираются точечно через `POST /api/users/resolve {"uuid": …}` —
   в 2.8.1 он возвращает `id`. Кого панель не знает вовсе — оставляем `NULL`
   и перечисляем в логе поимённо: это кандидаты на ручной разбор, а не повод
   ронять старт.
2. **Ленивое восстановление на 3.x.** Если бот впервые запустился уже на 3.x, а в
   БД только UUID — резолв по UUID невозможен (в 3.x его нет). Спасает Telegram ID:
   `GET /api/users/stream?telegramId=<id>` даёт `id` пользователя. Все наши записи
   создавались с `telegramId` (и регистрация, и `cmd/migrator`), так что путь
   рабочий для всей базы. Восстановление делается по требованию — в момент первого
   обращения к пользователю, — и результат сразу пишется в БД.
3. **Плановая доливка.** Тот же scheduler, что уже сверяет пользователей панели с
   БД по `TelegramID` (`internal/bot/scheduler.go:88`), попутно проставляет
   недостающие `remnawave_id`. Это бесплатно: список пользователей панели там уже
   загружен.

Если по Telegram ID нашлось больше одного пользователя панели (теоретически
возможно — панель не запрещает дубликаты `telegramId`), связку **не** пишем:
логируем ошибку и уведомляем владельца. Молча выбрать первого — значит с
некоторой вероятностью привязать чужой аккаунт к платежу.

### Что делать с `remnawave_uuid` дальше

Колонка остаётся заполненной для всех, кто создан на 2.8.x, и служит страховкой
на случай отката панели. Новые записи на 3.x пишут только `remnawave_id`.
`GetUserByRemnawaveUUID` сохраняется, к нему добавляется `GetUserByRemnawaveID`.
Удаление колонки — отдельная работа, не раньше чем через несколько релизов после
того, как владелец окончательно останется на 3.x.

## Порядок выката

Последовательность обязательная, потому что апгрейд панели удаляет UUID
безвозвратно:

1. Снять копию `bot.db` (перестройка таблицы `users` необратима).
2. Выкатить бота с поддержкой обеих версий. Панель ещё 2.8.x.
3. Убедиться по логам, что backfill прошёл: в базе не осталось строк с
   `remnawave_id IS NULL` (кроме тех, кого панель уже не знает — их бот перечислит
   в логе поимённо).
4. Обновить панель до 3.x. Дополнительных переменных окружения релизная 3.x не
   требует; на бэкенде отработают Prisma-миграции, включая `DROP COLUMN uuid`.
5. Проверить, что бот подхватил смену версии: в логе — сообщение о новой версии
   панели, и один сквозной сценарий (карточка подписки → устройства) отвечает.

### Если панель уже обновлена, а бот — нет

Это не катастрофа, но порядок действий другой. Старый бот ломается сразу; новый,
выкаченный на уже обновлённую панель, обязан при старте увидеть 3.x и запустить
**массовый проход восстановления**: для каждой строки с пустым `remnawave_id`
поиск по `telegram_id` через `stream` и запись найденного `id`. Это дороже
backfill-а (один запрос на пользователя вместо одного на всю базу), поэтому
проход идёт в фоне, не блокируя старт, с паузой 100 мс между запросами и логом
прогресса. Кого панель не знает вовсе — остаётся `NULL` и перечисляется в логе
поимённо, ровно как в 2.8.x-ветке: это кандидаты на ручной разбор, а не повод
ронять старт.
До того как проход дойдёт до конкретного пользователя, его выручает то же ленивое
восстановление при первом обращении. Данные не теряются ни в одном из сценариев.

Помимо самих вызовов клиента, UUID пользователя протёк в структуры и хелперы —
их надо перевести на `UserRef`, иначе на 3.x они молча получат пустую строку:

| Место | Что не так на 3.x |
|---|---|

| `internal/bot/devices.go:36` | `user.RemnawaveUUID == ""` как признак «подписки нет» — на 3.x пусто у всех, экран устройств отвалится для каждого |
| `internal/bot/admin.go:31,188,573-594` | `adminSession.UserUUID` — идентификатор в in-memory сессии админки; становится `UserRef` |
| `internal/bot/subscription_card.go` | `GetUserHwidDevicesCount(remUser.UUID)` — UUID берётся из ответа панели, на 3.x он пуст; заменяется на `remUser.Ref()` |
| `internal/bot/handlers.go:698` и другие `slog` | в логах поле `remnawave_uuid`; добавить `remnawave_id`, иначе разбор инцидентов на 3.x станет вслепую |
| `internal/database/invites.go:42,678,718` | `Subscriber.RemnawaveUUID` и `SELECT u.remnawave_uuid` в статистике рефералов; поле сейчас никем не читается — либо убрать, либо завести рядом `RemnawaveID` |
| `internal/bot/startup.go:79` `isRemnawaveNotFound` | сравнение текста ошибки с `"API error 404"`; заменяется на `errors.Is(err, ErrUserNotFound)` |

| `cmd/backfill-used-at/main.go:113` | `client.GetUser(user.RemnawaveUUID)` — отдельная утилита, про которую легко забыть; ломает сборку всего репозитория |
| `internal/remnawave/client.go:110` | `UpdateUserRequest.UUID` — публичное поле, которое заполняет вызывающий код (`admin.go:594`); идентификатор должен подставлять клиент |

Заодно два метода клиента стоит не переносить, а убрать: `ResetUserTraffic`

вызовов незачем; если `GetUserByRemnawaveUUID` решат оставить как симметрию к

## Попутно найденное

**`GetUserByTelegramID` разбирает ответ неверно, и это чинится вместе с переходом.**
По спеке 2.8.1 `GET /api/users/by-telegram-id/{telegramId}` возвращает `response`
**массивом** пользователей, а клиент (`client.go:190`) декодирует его в один объект
`User` — значит метод всегда возвращает ошибку. Чинится так: на 2.8.x разбирать
массив и брать точное совпадение по `telegramId`, на 3.x — `stream?telegramId=`.
Оба пути возвращают `(nil, nil)` при отсутствии пользователя, а не ошибку.
Обе ветки поиска и `ResolveUserByUUID` вынесены в `internal/remnawave/lookup.go`.

Смена контракта задевает **семь** вызовов, и каждый надо пройти руками:

| Вызов | Что происходит после починки |
|---|---|
| `startup.go:34` | **Ломается, если не тронуть.** Ветка «пользователя нет» сейчас ждёт *ошибку* (`isRemnawaveNotFound` → `UnclaimInvite`); при `(nil, nil)` код пойдёт дальше и разыменует `remoteUser.Username` на строке 46 — паника при старте, до запуска бота. Нужна явная ветка `remoteUser == nil → UnclaimInvite` |
| `payment_handler.go:49` | оживает проверка «подписка оплачена более чем на 90 дней вперёд» — продление начнёт блокироваться, как и задумывалось |
| `handlers.go:336` | оживает grace-экран |
| `handlers.go:818` | оживает выбор текста кнопки и скрытие оплаты |
| `payment.go:210` | в сообщении об оплате появится реальная дата окончания |
| `payment.go:514` | ветка сверки состояния подписки при ручной проверке платежа |
| `bug_report.go:286` | в репорт админу начнёт попадать реальный статус подписки |

Это не побочный эффект, а осознанная часть работы: шесть веток поведения, которые
сейчас мертвы, включатся разом. Пользователи увидят изменения в UX (в первую
очередь блокировку продления при запасе больше 90 дней), поэтому пункт стоит
пройти отдельным тикетом и проверить каждый сценарий вручную.

**Ошибка «пользователь не найден» ловится по подстроке.** `isRemnawaveNotFound`
(`startup.go:79`) сравнивает текст `"API error 404"`. Клиент должен возвращать
честную `ErrUserNotFound`, а `errors.Is` — заменить сравнение строк. Признак —
именно HTTP-статус `404`: в 3.2.3 тело ошибки описано схемой
`{timestamp, path, message, errorCode}` с кодом `A025`, а в 2.8.1 у `404` тело в
спеке вообще не описано. Значит опираться на `errorCode` как на единственный
признак нельзя — он используется только для уточнения текста в логе, если тело
разобралось. Заодно `doRequest` стоит научить возвращать типизированную ошибку с
полями «статус + errorCode + тело», чтобы `401`/`403` (см. выше) и `400` (сигнал
к ре-детекту версии) различались без разбора строк.

Итоговый вид этой части — `internal/remnawave/errors.go`: типизированная
`APIError{StatusCode, ErrorCode, Message, Body}`, часовой `ErrUserNotFound` для
`404` (проверяется через `errors.Is`), `APIStatusCode` для доступа к коду и
предикат `IsAuthError` для `401`/`403`. Сравнения текста ошибки с
«API error 404» заменены на `errors.Is` **в обоих** местах, где они были, —
`isAutoKickNotFoundError` и `isRemnawaveNotFound`.

## Краевые случаи

- **Апгрейд панели во время работы бота.** Первый же вызов ловит `400`, клиент
  перечитывает версию и повторяет запрос — пользователь ничего не замечает.
- **Откат панели на 2.8.x.** Возможен только восстановлением дампа Postgres:
  Prisma-миграции назад не откатываются, а `uuid` физически удалён. После
  восстановления дампа пользователи, созданные на 3.x, в панели исчезнут — бот
  увидит их как «нет в панели» и отработает обычной веткой `ErrUserNotFound`.
  Для остальных `remnawave_uuid` в нашей базе на месте, и клиент, определив 2.8.x,
  снова пойдёт по UUID. Если UUID почему-то не сохранился, его можно добрать через
  `POST /api/users/resolve {"id": …}` — в 2.8.1 ответ содержит `uuid`, — но только
  для пользователей, которые в восстановленном дампе вообще есть. Отдельно чинить
  нечего; пункт зафиксирован, чтобы никто не рассчитывал на бесшовный откат.
- **Панель недоступна на старте.** Бот стартует, версия неизвестна, вызовы к панели
  возвращают понятную ошибку; функции, не требующие панели, работают.
- **Пустая панель при детекте.** Мы опираемся на `metadata`, а не на форму ответа
  `GET /api/users`, поэтому пустая база панели ничего не ломает.
- **Пользователь есть в БД, но `remnawave_id` пуст, и в панели его нет.** Ленивое
  восстановление не находит — возвращаем `ErrUserNotFound`, и дальше работают
  существующие ветки обработки (reconcile, автокик, «вы не зарегистрированы»).
- **Гонка между ленивым восстановлением и плановой доливкой.** Запись
  `remnawave_id` идемпотентна (`UPDATE users SET remnawave_id = ? WHERE telegram_id = ?`),
  уникальный индекс не даст привязать один и тот же `id` к двум Telegram ID. На
  практике это придёт как обычная ошибка `Exec` с текстом
  `UNIQUE constraint failed: users.remnawave_id`, и её нельзя спутать с «база
  недоступна»: такую ошибку логируем как рассинхрон с обоими telegram_id,
  уведомляем владельца и **продолжаем** проход по остальным пользователям.
- **Версия панели новее 3.x.** Работаем по контракту 3.x и предупреждаем в логе;
  молча ломаться при выходе 4.0 бот не должен, но и гадать за него мы не будем.
- **`DELETE` возвращает 204.** Текущая проверка `resp.StatusCode >= 400` это уже
  переживает; тест на 204 добавляем явно, чтобы не потерять при рефакторинге.

## Тестирование

Обязательный минимум — по одному тесту на каждый способ сломаться, найденный выше:

- Юнит-тесты клиента через существующий `roundTripFunc`: для каждой операции — два
  теста (v2 и v3), проверяющие путь, тело и разбор ответа.
- Тест детекта: `metadata` отдаёт `2.8.1` / `3.2.3` / мусор / 500; запасная проба
  при `403` на `metadata`.
- Тест смены версии на лету: первый запрос → `400`, `metadata` → новая версия,
  повтор → `200`; негативный — повтор тоже `400`, ошибка уходит наверх; и
  контрольный: `404` ре-детект **не** запускает.
- `go test -race` на конкурентный доступ к кэшу версии: N параллельных вызовов при
  смене версии дают ровно один запрос `metadata`.
- Тест `expireAt`: отправляемое значение заканчивается на `Z` (иначе 3.x ответит 400).
- Тест `DELETE`, отвечающего `204` без тела.
- БД: чтение строки, где `remnawave_uuid IS NULL` (без этого теста ловушка с
  `Scan` вернётся при первом же рефакторинге).
- БД: две подряд вставки пользователей без UUID — обе проходят (проверка, что
  пишется `NULL`, а не `""`).
- Миграция: старая база с `NOT NULL` → перестройка → **каждая** из девяти колонок
  на месте с прежними значениями (отдельно `legacy_paid_migrated`, у неё
  `NOT NULL DEFAULT 0`), число строк совпадает, индексы существуют.
- Миграция на свежей базе: перестройка не запускается вовсе.
- Backfill: панель 2.8.x, три пользователя, у одного `remnawave_id` уже есть.
- Ленивое восстановление на 3.x, включая случай «по `telegram_id` нашлось двое» —
  связка не пишется, уходит алерт.
- Доливка при конфликте: `UNIQUE constraint failed` логируется, проход не прерывается.
- `startup.go`: `GetUserByTelegramID` вернул `(nil, nil)` → инвайт освобождён,
  паники нет.
- Ручная проверка на живой панели 2.8.1 (у владельца) и на поднятой локально 3.2.3
  до выката — включая `PATCH` без `id` (см. правило 3 детекта).

## План работ

1. `internal/remnawave`: `APIVersion`, `UserRef`, потокобезопасный детект и кэш
   версии, ветвление путей и тел, `User.ID`/`Ref()`, `ResolveUser`,
   типизированные ошибки со статусом. Тесты на обе версии.
2. Поиск пользователя по Telegram ID: починка v2-разбора + v3 через `stream` +
   правка всех семи вызовов, отдельно `startup.go` (иначе паника при старте).
3. Миграция БД: правка базового DDL, `remnawave_id`, перестройка `users` в
   транзакции, `RemnawaveUUID *string` и NULL-safe чтение, запись `NULL` вместо
   `""`, методы доступа. Тесты миграции.
4. Шов `b.userRef(telegramID)` и перевод вызывающего кода на `UserRef` — bot,
   migrator, `cmd/backfill-used-at`, `cmd/bot/main.go`. `go build ./...` зелёный.
5. Backfill на 2.8.x при старте + доливка в scheduler + ленивое восстановление на
   3.x + массовый фоновый проход, если бот стартовал уже на 3.x.
6. Ре-детект версии: инвалидация кэша по `400` и периодическая сверка в scheduler.
7. Документация: `CLAUDE.md`/`AGENTS.md`/`README.md` — ссылка на новую спеку API,
   раздел о поддержке двух версий панели и порядок обновления из этой спеки.

Пункты 1–3 независимы и могут идти параллельно; 4 зависит от 1 и 3; 5–6 — от 4.
Пункт 2 стоит вести отдельным тикетом: он оживляет шесть ранее мёртвых веток UX.
