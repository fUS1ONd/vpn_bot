# План: интеграция ЮKassa как второго провайдера оплаты

Дата: 2026-07-16  
Статус: согласован для реализации

## Цель

Добавить ЮKassa как необязательный второй платёжный провайдер, не нарушив текущие
платежи Platega, продление подписки, scheduler и финансовую статистику модераторов.

ЮKassa обслуживает рублёвые способы оплаты через собственную страницу: карта, СБП,
SberPay и другие методы, доступные конкретному магазину. Platega остаётся для криптовалюты.

## Зафиксированный UX

Если настроены оба провайдера, после кнопки оплаты бот показывает:

```text
💳 Подписка на 1 месяц — {цена} руб.

Выберите способ оплаты:
[⚡ Карта / СБП / SberPay]
[🪙 Криптовалюта]
[🚫 Отмена]
```

- `⚡ Карта / СБП / SberPay` создаёт redirect-платёж ЮKassa. Пользователь выбирает
  доступный метод уже на странице ЮKassa.
- `🪙 Криптовалюта` открывает существующий flow Platega с криптовалютой.
- Если доступен только один провайдер, скрывать недоступный вариант и не предлагать
  пользователю заведомо неработающий способ.
- После создания платежа для обоих провайдеров использовать один экран ожидания:
  ссылка на оплату, `🔄 Проверить оплату`, `🚫 Отмена`.

## Архитектурные решения

1. Ввести нейтральный интерфейс платёжного провайдера вместо распространения
   зависимостей `platega.Client` по bot/callback-коду.
2. Реализовать `internal/yookassa` напрямую через HTTP API v3: HTTP Basic Auth,
   `Idempotence-Key`, создание redirect-платежа с `capture: true`, получение статуса.
3. В ЮKassa передавать `metadata.local_payment_id` после создания локальной записи
   либо другой неизменяемый correlation ID. В любом случае webhook сопоставлять с
   сохранённым внешним ID, а не с данными, присланными пользователем.
4. `return_url` использовать только для возврата в Telegram; он не подтверждает
   оплату и не активирует подписку.
5. Входящий webhook ЮKassa считать подсказкой: перед активацией получить актуальный
   платёж по API и сверить его ID, статус `succeeded`, сумму, валюту и получателя
   (`shopId`) с локальной записью. IP allowlist допустим как дополнительная защита.
6. Платёж зачисляется только при `succeeded`. Для выбранного одностадийного сценария
   `waiting_for_capture` не является успешной оплатой.
7. Комиссия провайдера должна быть нейтральной в модели и фиксироваться для платежа;
   настройки/названия Platega не могут использоваться для расчёта ЮKassa.

## Изменения данных и совместимость

### Таблица `payments`

Добавить миграцией:

- `provider TEXT NOT NULL DEFAULT 'platega'`;
- `provider_payment_id TEXT`;
- уникальный индекс по `(provider, provider_payment_id)` для непустых идентификаторов.

Для существующих строк заполнить `provider_payment_id` из
`platega_transaction_id`. Старое поле и индекс сохранить на время обратной
совместимости, затем обращаться в новом коде только к нейтральным полям.

`payment_method` оставить бизнес-методом. Для ЮKassa сохранять фактический тип
метода из объекта платежа, когда он становится известен, либо значение `yookassa`
для агрегированного метода до уточнения.

Переименовать внутри Go-модели и финансовой логики Platega-специфичные сущности
(`PlategaTransactionID`, `PlategaFee`) в нейтральные с безопасной миграцией данных.

## План реализации

### 1. Контракты и миграция БД

- Ввести типы провайдера и нейтральные поля платежа.
- Написать SQLite-миграцию, backfill исторических Platega-платежей и индексы.
- Обновить CRUD-запросы и тесты БД: поиск по внешнему ID с учётом провайдера,
  pending-платёж, история и начисления.

**Критерий:** старая БД открывается без потери истории; существующий flow Platega
находит свои платежи после миграции.

### 2. Клиент ЮKassa

- Создать `internal/yookassa/client.go` с запросами `POST /v3/payments` и
  `GET /v3/payments/{id}`.
- Для создания использовать рублёвую сумму с двумя знаками, `capture: true`,
  `confirmation.type: redirect`, `return_url`, description и metadata.
- Генерировать уникальный `Idempotence-Key` на одну попытку создания; при сетевой
  неопределённости повторять запрос только с тем же ключом.
- Покрыть тестами Basic Auth, заголовок идемпотентности, body, статусы и ошибки API.

**Критерий:** клиент корректно обрабатывает `pending`, `succeeded`, `canceled` и
возвращает `confirmation_url`.

### 3. Конфигурация и состав Bot

- Добавить `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, `YOOKASSA_RETURN_URL`,
  `YOOKASSA_FEE_PERCENT`; провайдер считается включённым только при паре ID/ключ.
- Добавить переменные в docker-compose, README, `.env.example` (если есть) и тесты
  config.
- Создавать клиент только когда ЮKassa настроена; Platega и ЮKassa могут работать
  одновременно или по отдельности.

**Критерий:** отсутствие переменных ЮKassa не меняет нынешнее поведение Platega.

### 4. Выбор способа оплаты и создание платежа

- Заменить Platega-специфичное состояние выбора метода на выбор доступного
  провайдера/сценария.
- Реализовать согласованный UX: ЮKassa для рублёвых методов, Platega для крипты.
- Обобщить create-flow: проверка цены, лимита 90 дней, мьютекс пользователя,
  переиспользование ссылки того же pending-платежа и истечение альтернативного.
- Сохранять провайдера, внешний ID, ссылку и срок платежа.

**Критерий:** два быстрых выбора не создают две активные ссылки; выбор второго
провайдера корректно истекает первую pending-ссылку.

### 5. Webhook и ручная проверка

- Добавить `POST /yookassa/webhook` в callback-сервер и отдельный handler payload.
- При webhook запросить платёж у ЮKassa и провести все проверки из архитектурного
  решения; отвечать 200 только после безопасной обработки либо для заведомо
  неизвестного/устаревшего события по согласованной политике retry.
- Обобщить callback-обработчик статусов: успешная оплата → текущая идемпотентная
  активация; отмена → canceled; возвраты/chargeback рассмотреть отдельно по
  поддерживаемым событиям и бизнес-политике.
- Кнопка `🔄 Проверить оплату` запрашивает статус через того провайдера, который
  создал pending-платёж.

**Критерий:** поддельный webhook не активирует доступ; реальный `succeeded` и ручная
проверка приводят к одной активации без дублирования.

### 6. Финансы, scheduler и документация

- Сделать расчёт earnings провайдер-независимым, определить и документировать
  источник процента комиссии ЮKassa.
- Убедиться, что scheduler обрабатывает `confirmed_not_activated` независимо от
  провайдера.
- Обновить пользовательские и админские тексты, README и документацию деплоя.
- Описать отдельно обязательный для владельца магазина процесс фискализации/чеков;
  реализацию receipt не добавлять без подтверждённых реквизитов и юридического
  сценария.

**Критерий:** статистика не применяет тарифы Platega к платежам ЮKassa; старые
платежи и начисления отображаются без изменений.

### 7. Проверка

- Добавить unit-тесты клиенту, конфигурации, БД, callback-валидации и обработчикам
  Telegram.
- Прогнать `make fmt` и `make tests`.
- В тестовом магазине ЮKassa провести как минимум successful и canceled платежи,
  проверить webhook, ручную проверку и повторную доставку события.
- Перед production включением отдельно проверить чеки/фискализацию с владельцем
  магазина и тестовым платежом.

## Вне объёма этого изменения

- Автоплатежи и сохранение платёжных средств.
- Виджет ЮKassa на собственной веб-странице: для Telegram достаточно redirect.
- Возвраты из админ-панели.
- Изменения конфигурации Caddy в этом плане: они выполняются и проверяются отдельно
  во время развёртывания.

## Открытые решения до начала шага 6

1. Точная договорная комиссия ЮKassa и нужно ли задавать её одним процентом или
   по фактическому способу оплаты.
2. Юридический статус получателя платежей и способ фискализации: Чеки от ЮKassa,
   внешняя касса или отдельный процесс самозанятого.
3. Бизнес-политика по возврату ЮKassa: немедленное отключение, ручная модерация или
   отдельный grace-процесс.
