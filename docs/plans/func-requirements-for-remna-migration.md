# Этап 1: Подготовка фундамента и Редизайн архитектуры

**Цель этапа:** Подготовить репозиторий к смене движка, определить новые структуры данных и интерфейсы взаимодействия, очистить проект от легаси.

### 1.1. Управление версиями и Очистка (Housekeeping)

- **Создание ветки:** Вся работа должна вестись в изолированной ветке `v2`.
- **Удаление устаревших модулей:**
  - `internal/threexui`: Клиент 3X-UI полностью удаляется.
  - `internal/vless`: Генератор ссылок больше не нужен (ссылки генерирует панель).
  - `internal/subscription`: Встроенный HTTP-сервер подписок удаляется.
  - `internal/database`: Старая логика работы с БД (платежи, сложные подписки) помечается на удаление или полную перезапись.

### 1.2. Проектирование Конфигурации (Config Design)

Необходимо определить новый набор переменных окружения (`.env`), который заменит старый.

- **Удалить:** Все переменные, связанные с `SERVER_A`, `SERVER_B`, `SERVER_C` (credentials, hostnames, keys).
- **Добавить:**
  - `REMNAWAVE_URL`: Адрес API панели.
  - `REMNAWAVE_API_TOKEN`: Токен администратора для управления пользователями.
  - `DB_PATH`: Путь к новой базе данных (по умолчанию `users_v2.db`).
- **Оставить:** `BOT_TOKEN`, `ADMIN_ID`.

### 1.3. Проектирование Схемы Данных (Database Schema)

Мы переходим на "чистую" схему. Старый файл БД будет заархивирован, новый создается с нуля.

**Таблица `users` (Упрощенная):**

- **Назначение:** Хранить только идентификаторы для связи Telegram и Remnawave.
- **Поля:**
  - `telegram_id` (Primary Key / Unique): Для идентификации в боте.
  - `username`: Для удобства админа.
  - `remnawave_uuid`: UUID пользователя в панели Remnawave (получаем от API при создании).
  - `created_at`: Дата регистрации.
- _Исключено:_ Поля `expiry`, `traffic_limit` (теперь это зона ответственности Remnawave).

**Таблица `invites` (Новая):**

- **Назначение:** Реализация системы доступа "только для своих".
- **Поля:**
  - `code`: Уникальная строка-ключ.
  - `created_by`: ID админа, создавшего ключ.
  - `used_by`: ID пользователя, активировавшего ключ (Nullable).
  - `is_used`: Флаг использования.

### 1.4. Проектирование Интерфейса API Клиента (Remnawave Client)

Необходимо спроектировать абстракцию для общения с Remnawave, чтобы бизнес-логика бота не знала деталей HTTP-запросов.

**Ключевые методы клиента:**

1.  **`CreateUser(tgID, username)`**:
    - Создает пользователя в панели.
    - Устанавливает лимит трафика (30 GB).
    - Устанавливает "вечный" срок действия.
    - Возвращает: `UUID` нового пользователя и `Subscription URL`.
2.  **`GetUser(uuid)`**:
    - Получает текущую статистику (использовано / всего трафика).
    - Проверяет статус (активен/заблокирован).
3.  **`ResetTraffic(uuid)`** (Опционально):
    - Для ручного сброса трафика админом.

### 1.5. Подготовка к Миграции

- Определить формат хранения старой базы данных (например, переименование в `users_archive.db`).
- Спланировать логику утилиты-мигратора, которая будет читать старую БД и использовать новый API Клиент для переноса.

---

**Результат этапа:**
В репозитории создана новая ветка, удален старый код, подготовлена структура папок для новых пакетов (`internal/remnawave`, `internal/core`), и утверждена схема БД. Код еще не написан, но место для него расчищено и размечено.

# Этап 2: Разработка Инструментов Миграции (The Migrator)

**Цель этапа:** Создать надежный, изолированный инструмент (CLI-утилиту), который автоматизирует перенос пользователей из старой архитектуры в новую. Ручной перенос исключен во избежание ошибок.

Этот инструмент будет одноразовым: он запускается один раз при деплое, выполняет работу и больше не используется.

### 2.1. Концепция ETL-скрипта (`cmd/migrator`)

Мы реализуем классический процесс **ETL** (Extract, Transform, Load). Утилита будет работать независимо от основного бота.

**Входные данные:**

- Файл старой базы данных (`users.db`).
- Доступы к API Remnawave (URL + Token).

**Выходные данные:**

- Файл новой базы данных (`users_v2.db`) с заполненной таблицей пользователей.
- Созданные аккаунты в панели Remnawave.
- Отчет о миграции (лог-файл).

### 2.2. Логика работы (Workflow)

1.  **Extract (Чтение):**
    - Скрипт подключается к старой SQLite базе в режиме "только чтение".
    - Выбирает всех пользователей, у которых поле `telegram_id` не пустое.
    - _Фильтрация:_ Мы игнорируем старые статусы подписок (истекла/активна) и поля трафика. Мы берем только **идентичность** (кто это?) — ID и Username.

2.  **Transform (Преобразование):**
    - Применяет новую бизнес-логику "Flat Membership":
      - Каждому пользователю назначается лимит **30 GB**.
      - Срок действия устанавливается как **NULL** (бессрочно).
    - Формирует "Note" (заметку) для Remnawave: _"Migrated from v1 | @username"_.

3.  **Load (Загрузка и Синхронизация):**
    - **Шаг А (API):** Для каждого пользователя отправляется синхронный запрос в Remnawave API (`Create User`).
    - **Шаг Б (Обработка ответа):** API возвращает уникальный `UUID` созданного пользователя и ссылку на подписку.
    - **Шаг В (Сохранение):** Скрипт записывает связку `telegram_id` <-> `remnawave_uuid` в **новую** базу данных (`users_v2.db`).

### 2.3. Режимы безопасности

Чтобы не "замусорить" панель Remnawave дублями или ошибками во время тестов, мигратор должен поддерживать флаги запуска:

- **`--dry-run` (Холостой прогон):**
  - Скрипт читает старую базу.
  - Выводит в консоль: _"Будет создан пользователь ID 12345, Username: @test"_.
  - **НЕ** отправляет запросы в API.
  - **НЕ** пишет в новую БД.
  - _Цель:_ Убедиться, что мы правильно читаем старые данные перед реальным запуском.

- **`--live` (Боевой режим):**
  - Выполняет реальные запросы и запись.

### 2.4. Обработка исключений (Edge Cases)

- **Пользователь уже есть в Remnawave:** Если API вернет ошибку "User already exists" (маловероятно при чистой панели, но возможно), скрипт должен залогировать это и попытаться найти этого юзера, чтобы обновить запись в локальной БД, а не падать с ошибкой.
- **Сбой сети:** Если API Remnawave недоступно, скрипт должен остановиться и сохранить прогресс (или просто позволить перезапустить его, пропуская уже мигрированных).

---

**Результат этапа:**
Готовая консольная программа `migrator`, протестированная в режиме `--dry-run`. Мы уверены, что при запуске она корректно перенесет всех твоих родственников и друзей в новую систему за пару секунд.

# Этап 3: Реализация Логики Бота и Интерфейса (UI)

**Цель этапа:** Вдохнуть жизнь в бота. Мы заменяем "мозги" бота: вместо того, чтобы управлять серверами напрямую, он станет "пультом управления" для API Remnawave и локальной базы инвайтов.

Это финальный этап разработки кода, после которого систему можно запускать.

### 3.1. Рефакторинг Точки Входа (`main.go`)

Файл инициализации нужно полностью переписать.

- **Удалить:** Инициализацию трех клиентов `threexui`, запуск HTTP-сервера `subscription`, старые крон-задачи (scheduler) по сбросу трафика (Remnawave делает это сам).
- **Добавить:**
  - Инициализацию нового `remnawave.Client`.
  - Подключение к новой базе данных (`users_v2.db`).
  - Запуск бота с передачей ему этих двух зависимостей.

### 3.2. Логика "Привратника" (Onboarding Flow)

Самое важное изменение в логике `/start`. Бот превращается в закрытый клуб.

1.  **Проверка при входе:**
    - Когда пользователь пишет `/start` (или любое сообщение), бот проверяет таблицу `users` по `telegram_id`.
2.  **Ветвление:**
    - **Пользователь найден:** Показываем **Главное Меню**.
    - **Пользователь НЕ найден:**
      - Бот скрывает меню.
      - Отправляет сообщение: _"🔒 Доступ ограничен. Пожалуйста, введите код приглашения."_
      - Переводит пользователя в состояние `StateWaitInvite`.

### 3.3. Обработка Инвайтов (`HandleInvite`)

Новый обработчик текстовых сообщений для состояния `StateWaitInvite`.

1.  **Валидация:** Проверяет полученный код в таблице `invites` (существует ли, не использован ли).
2.  **Активация (Транзакция):**
    - Вызов `Remnawave.CreateUser(tg_id)`.
    - Получение `UUID` от панели.
    - Запись пользователя в таблицу `users`.
    - Пометка инвайта как `is_used = true`.
3.  **Финиш:** Отправляет приветствие и открывает Главное Меню.

### 3.4. Обновление Главного Меню (Handlers)

Мы переписываем реакции на кнопки, оставляя визуальную часть (тексты кнопок) привычной.

- **👤 Мой статус:**
  - _Было:_ Бот считал трафик сам или брал из кэша.
  - _Станет:_ Бот делает живой запрос `Remnawave.GetUser(uuid)`.
  - _Вывод:_ "Трафик: **12.5 / 30 GB**. Сброс лимита: 1-го числа". (Информацию о сроке действия убираем, так как подписка вечная).

- **🌐 Подключить (Получить настройки):**
  - _Было:_ Ссылка на IP бота (`http://1.2.3.4:8000/sub/...`).
  - _Станет:_ Бот отдает прямую ссылку на Subscription URL из панели Remnawave (обычно это `https://domain.com/api/sub/UUID`).
  - _UX:_ Пользователь просто копирует эту ссылку в свое приложение (v2rayNG/Streisand).

- **💸 Поддержать (Донат) [НОВОЕ]:**
  - Простой хендлер, который отправляет статический текст:
    > "Сервер работает благодаря вашей поддержке ❤️
    > Перевод по СБП: `+7 999 000-00-00` (Т-Банк)
    > Получатель: Константин К."

- **📚 Инструкции:**
  - Оставляем как есть (тексты актуальны, меняется только ссылка, которую пользователь вставляет).

### 3.5. Админ-команды (Внутри бота)

Добавляем функционал для генерации инвайтов, чтобы тебе не лазить в базу данных руками.

- Команда `/invite`:
  1.  Генерирует случайную строку (например, 8 символов).
  2.  Сохраняет в таблицу `invites`.
  3.  Отдает тебе сообщение: _"Ключ создан: `ABC-123`. Передай его другу."_

**Результат этапа:**
Полностью рабочий бот с новой логикой.

- "Свои" (мигрированные на Этапе 2) сразу видят меню и пользуются.
- "Чужие" видят просьбу ввести инвайт.
- Ты можешь генерировать инвайты прямо в чате.
