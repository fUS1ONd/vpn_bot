# Внедрение dev-guidelines в vpn_bot

**Дата:** 2026-07-08
**Ветка реализации:** `chore/dev-guidelines-adoption` (создать от `main`)
**Базовый коммит:** f662096
**Источник правил:** `~/dev-guidelines` (workflow.md, harness.md, token-economy.md, antipatterns.md, checklists/new-project.md)

## Зачем

vpn_bot — эталонный проект по процессу (есть `docs/plans`+`docs/progress`, Makefile,
CI, `.env.example`), но накопились расхождения с каноном dev-guidelines. Цель волны —
закрыть их, ничего не сломав. Каждая задача атомарна, коммитится отдельно, гейты
после каждой.

## Гейты (после каждой задачи)

```bash
gofmt -l .            # пусто = ок
go vet ./...
go build ./cmd/bot/...
go test ./...
```

Изменения только в документации/конфигах — код не трогаем, поэтому гейты должны
оставаться зелёными без усилий. Задача 3 добавляет `make ci-local`, дальше гонять его.

## Задача 1. Почистить CLAUDE.md (antipatterns #7)

**Проблема.** CLAUDE.md — 206 строк. Раздел «Важные заметки» (пп. 1–17) содержит
детали реализации. Пункт 17 (admin-extend) — ~30 строк: имена функций, сигнатуры
(`applyAdminExtend`, `nextMonthExpireAt`, `extendedSubscriptionMessage`), устройство
мьютексов и кулдаунов. Это changelog в CLAUDE.md — платим токенами каждую сессию,
важные правила тонут.

**Тест каждой строки:** «уберу — агент начнёт ошибаться?» Нет → в docs/, сюда ссылка.

**Действия:**
1. Создать `docs/architecture/notes.md` (или `docs/notes/`) — перенести туда детали
   реализации из пп. 1–17, сгруппировав по подсистемам (платежи, инвайты, мониторинг,
   admin-extend, устройства, багрепорт).
2. В CLAUDE.md оставить от «Важных заметок» только те строки, что реально меняют
   поведение агента (неочевидные гочи-однострочники), с ссылкой на `docs/architecture/notes.md`
   за деталями. Ориентир: раздел ужимается с ~60 до ~10–15 строк.
3. Пункт 17 (admin-extend) целиком → в notes.md. В CLAUDE.md его не оставлять:
   фича стабильна, деталей реализации агент не должен держать в контексте всегда.
4. Раздел «Переменные окружения» (пп. 40–77) — оценить: он большой и дублирует
   `.env.example`. Кандидат на «см. `.env.example`» + оставить в CLAUDE.md только
   те, у которых есть неочевидная семантика (опциональность, влияние на flow).
5. Целевой размер CLAUDE.md — ~100 строк (потолок из шаблона).

**Гейт задачи:** `wc -l CLAUDE.md` ≤ ~110; агентских команд/конвенций не потеряли
(сверить с templates/CLAUDE.md.template — команды, коммиты, секреты, ссылки на docs).

**Осторожно:** не выкинуть реальные гочи (сброс трафика 1-го числа, опциональность
Platega/сквадов/render, «удалять только неиспользованные коды» — это правила, а не
changelog). Разделять «правило поведения» (оставить) vs «как устроена фича» (в docs).

## Задача 2. Свести AGENTS.md и CLAUDE.md к одному источнику

**Проблема.** `AGENTS.md` (129 строк) — рассинхронизированная копия CLAUDE.md
(начинается с `# CLAUDE.md`). Два источника правды разъезжаются; Codex читает
AGENTS.md, Claude — CLAUDE.md, получают разное.

**Решение (выбрать консервативно):**
- Вариант А (рекоменд.): `AGENTS.md` → тонкий указатель: «Правила проекта — в
  `CLAUDE.md`, читай его». Один канонический файл (CLAUDE.md), AGENTS.md только

- Вариант Б: симлинк `AGENTS.md -> CLAUDE.md`. Проще, но симлинки в git иногда
  сюрпризят на Windows/CI-чекаутах — для этого репо неактуально (Linux), но А надёжнее.

**Действия:** сделать это ПОСЛЕ задачи 1 (чтобы указывать на уже почищенный CLAUDE.md).
Заменить содержимое AGENTS.md на короткий редирект. Проверить, что уникального
контента (которого нет в CLAUDE.md) в AGENTS.md не теряем — сначала `diff`.

**Гейт:** в репозитории один канонический свод правил; AGENTS.md ≤ 5 строк.

## Задача 3. `make ci-local` + локальный гейт (antipatterns #4, checklist)

**Проблема.** CI (`.github/workflows/deploy.yml`, job `ci`) гоняет нативно:
`gofmt -l .` → `go vet ./...` → `go build ./cmd/bot/...` → `go test ./...`.
Локальные `make tests`/`make fmt` завязаны на docker и не зеркалят CI один-в-один.
«Зелёно локально» не гарантирует «зелёно в CI».

**Действия:**
1. Добавить в Makefile цель `ci-local`, повторяющую шаги CI-джоба ровно, нативным
   go (не через docker), в том же порядке:
   ```makefile
   ci-local: ## Локально прогнать те же проверки, что и CI
   	@test -z "$$(gofmt -l .)" || { echo "gofmt:"; gofmt -l .; exit 1; }
   	go vet ./...
   	go build ./cmd/bot/...
   	go test ./...
   ```
2. В CLAUDE.md (раздел команд) добавить `make ci-local` и правило:
   «Перед push — `make ci-local` зелёный. Красный ci-local = не пушим.»
3. Синхронизировать формулировку с `make fmt`/`make tests`: явно указать, что
   `ci-local` — это то, что решает, пройдёт ли CI.

**Гейт:** `make ci-local` проходит на текущем коде.

**Открытый вопрос для задачи 5:** согласовать `ci-local` с будущими добавлениями
(race, staticcheck) — если задача 5 расширяет CI, `ci-local` расширяется синхронно.

## Задача 4. Hooks + `.claude/settings.json` в git (harness.md, token-economy #7)

**Проблема.** Жёсткие правила («красный fmt = стоп», антидамп `.env`) держатся на
совести модели (CLAUDE.md — совещательный). В git только `settings.local.json`
(личный, не коммитится). Нет детерминированных ворот.

**Действия:**
1. Создать `.claude/settings.json` (в git) со следующими хуками:
   - **PostToolUse (Edit|Write, matcher по `.go`)** — прогнать `gofmt -w` на
     изменённом файле. Автоформат, чтобы `gofmt -l` в CI не падал.
   - **PreToolUse (Bash)** — антидамп секретов: блокировать `cat .env`,
     `docker exec ... env`, вывод `.env` целиком (пример хука — harness.md).
     vpn_bot держит прод-секреты (BOT_TOKEN, REMNAWAVE_API_TOKEN, PLATEGA_SECRET,
     пароль Postgres) — это прямая защита от antipatterns #10.
   - **Stop (только для Go-правок)** — ворота: `go test ./...` зелёные перед
     завершением хода, НО срабатывают только если в сессии менялся Go-код.
     Реализация: хук проверяет `git diff --name-only` (staged+unstaged) на
     наличие `*.go`; нет Go-изменений → exit 0 (пропустить, не мешать
     док-правкам); есть → `go test ./...`, красные → exit 2 + stderr.
     Решение зафиксировано (см. «Решения» ниже): не жёсткий always, не отказ —
     компромисс «страхуем код, не трогаем документацию».
2. `.gitignore` — убедиться, что `settings.local.json` игнорируется, а
   `settings.json` коммитится. Добавить `.claude/settings.local.json` в gitignore,
   если не покрыт.
3. Проверить хуки: `/hooks` в Claude Code + ручной прогон запрещённой команды
   (должна блокироваться с exit 2).

**Гейт:** `.claude/settings.json` в git; антидамп-хук блокирует `cat .env`;
автоформат-хук не ломает существующие правки.

**Осторожно:** хук должен читать JSON вызова со stdin через `jq` (см. пример в
harness.md), не хардкодить. Не заблокировать легитимные команды (`.env.example`
читать можно — точный grep, чтобы `.env.example` не попал под `cat .*\.env`).

## Задача 5. Оценка качества проверок CI/локально + что ещё стоит проверять

**Контекст.** Go 1.25, бот с конкурентностью (`sync.Map`, мьютексы `getPaymentMutex`,
scheduler каждые 30 мин, callback-сервер). Был целый design `concurrency-fixes`.
Текущий CI: `gofmt`, `go vet`, `go build`, `go test` (без `-race`).

**Проанализировать и предложить (не внедрять слепо — оценить стоимость/пользу):**

1. **`go test -race ./...`** — СИЛЬНЫЙ кандидат. Проект концуррентный, гонки —
   реальный класс багов здесь (история concurrency-fixes это подтверждает).
   Race-детектор ловит то, что не видят ни vet, ни обычные тесты. Стоимость:
   тесты медленнее в ~2–10×, но CI это терпит. → Рекомендация: добавить в CI и
   ci-local.
2. **staticcheck** (`honnef.co/go/tools`) или **golangci-lint** — статанализ уровнем
   выше `vet`: неиспользуемый код, подозрительные конструкции, багопаттерны.
   golangci-lint агрегирует много линтеров (включая staticcheck, gosimple,
   ineffassign). Оценить: не зашумит ли на существующей кодовой базе (может выдать
   сотни ворнингов на legacy). Стратегия — включить, зафиксировать baseline,
   чинить постепенно; либо начать с одного staticcheck.
3. **Покрытие тестами** — оценить `go test -cover`, понять голые места (payment,
   scheduler, admin-extend — критичны, деньги). Не гейт, а видимость: какие
   критические пути без тестов. Не блокировать PR по проценту (шумно), но
   зафиксировать текущий уровень.
4. **`govulncheck`** (`golang.org/x/vuln`) — сканер известных уязвимостей в
   зависимостях. Дёшево, гоняется отдельным шагом, полезно для прод-бота с
   платежами. Кандидат в CI (можно non-blocking сначала).
5. **`gofmt` → `gofumpt`?** — оценить, нужен ли более строгий формат.低 приоритет.
6. **Dockerfile / docker-compose линт** (hadolint) — низкий приоритет, оценить.

**Выход задачи 5** — не код, а секция в этом файле или отдельный
`docs/plans/2026-07-08-ci-quality-review.md` с таблицей «проверка / польза для
vpn_bot / стоимость / вердикт (внедрять сейчас/потом/нет)». Что решено внедрять
сейчас — добавить в CI (`deploy.yml`) и в `make ci-local` синхронно.

**Приоритет внедрения (предварительно, до анализа):**
- Сейчас: `-race` в тестах, `govulncheck` (non-blocking).
- Оценить и решить: staticcheck/golangci-lint (риск шума на legacy).
- Видимость без гейта: `-cover`.

## Зафиксированные решения (2026-07-08)

- **Метод разработки:** внедряем только базу (задачи 1–5). superpowers TDD/debugging,
  оркестратор автономных волн, формализация handoff/progress-цикла в CLAUDE.md —
  отложены до явной потребности.
- **Скиллы:** НЕ заводим в этой волне. По harness.md скилл оправдан только при
  (а) повторе между проектами и (б) задокументированном провале. Сейчас нет
  повторяющегося провала → писать скилл впрок нельзя. deploy-скилл и порт
  orchestrator — кандидаты на потом, когда провал будет записан.
- **Stop-хук:** вариант «только на `.go`» (см. задачу 4). Не жёсткий always
  (трение на док-сессиях), не отказ от ворот. Компромисс.

## Не в скоупе этой волны

- Скиллы (`.claude/skills/`) — см. «Решения»: нет задокументированного повода.
- Метод разработки за пределами базы (TDD/оркестратор/handoff-правила) — потом.

- Архивация старых `docs/plans` (40+ файлов) — отдельная гигиена, git-история хранит.
  Не срочно: планы не грузятся в контекст сами.
- Рефакторинг кода бота. Волна — только документация, конфиги, CI.
