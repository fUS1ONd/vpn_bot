# Прогресс: интеграция ЮKassa

План: [2026-07-16-yookassa-integration.md](../plans/2026-07-16-yookassa-integration.md)

## Выполнено

- Добавлены нейтральные поля `provider` и `provider_payment_id` с миграцией, backfill исторических Platega-записей и частичным уникальным индексом.
- Реализован HTTP-клиент ЮKassa v3: Basic Auth, уникальный `Idempotence-Key`, redirect payment с `capture: true`, metadata локального платежа и получение статуса.
- Добавлены опциональные настройки ЮKassa, одновременный выбор ЮKassa для рублёвых способов и Platega для криптовалюты, общий экран ожидания и проверка статуса через исходного провайдера.
- Webhook ЮKassa сопоставляет только сохранённый внешний ID, затем сверяет через API ID, сумму, RUB и `shopId`; входящее тело не активирует подписку самостоятельно.
- Комиссия ЮKassa учитывается отдельно через `YOOKASSA_FEE_PERCENT`; тарифы Platega к ней не применяются.
- Обновлены Docker/env/README. В README явно оставлено обязательное действие владельца магазина: подтвердить фискализацию и чеки до production-включения.
- Добавлены тесты клиента, миграции старой БД, конфигурации, клавиатур, финансовой изоляции комиссии и отклонения поддельного webhook.
- Независимое code review выявило и подтверждённо закрыло: подтверждение истёкшей альтернативной ссылки, повтор с потерянным ответом через сохранённый ключ, дробную сумму, snapshot комиссии, ручную проверку без верификации и маршрут webhook.

## Проверка

`go test ./internal/yookassa ./internal/database ./internal/config ./internal/callback ./internal/bot -count=1` — успешно.

## Перед развёртыванием

- Указать фактическую договорную ставку `YOOKASSA_FEE_PERCENT`.
- Провести в тестовом магазине successful и canceled платёж, webhook, ручную проверку и повторную доставку.
- Подтвердить фискализацию/чеки с владельцем магазина; receipt в код намеренно не добавлен без реквизитов и юридической схемы.
