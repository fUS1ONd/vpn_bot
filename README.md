# VPN Bot (Remnawave)

Telegram-бот управления VPN на базе [Remnawave](https://remnawave.com).
Пользователи регистрируются по инвайт-кодам, управляют подключениями и отслеживают трафик.
Поддерживает пользовательский и административный режимы.

## Быстрый старт

```bash
git clone https://github.com/<user>/vpn_bot.git
cd vpn_bot
cp .env.example .env
# Заполни .env своими ключами
make up
```

Логи:

```bash
make logs
```

### Публикация callback-сервера

Провайдеры доставляют уведомления об оплате только по HTTPS, поэтому встроенный
callback-сервер (`CALLBACK_PORT`, дефолт `8080`) публикуется наружу обратным прокси.
Отдельный домен не нужен — достаточно path-префикса на любом уже обслуживаемом домене:
внутренние роуты бота (`/platega/callback`, `/yookassa/webhook`, `/health`) при этом
не меняются. Пример для nginx:

```nginx
location = /vpn-bot/platega/callback {
    proxy_pass http://vpn-bot:8080/platega/callback;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    # Платёжные заголовки Platega (X-MerchantId, X-Secret) должны дойти до бота
    proxy_pass_request_headers on;

    # Бот отвечает вебхуку до 65 секунд (повторы запросов к кассе уложены в этот бюджет)
    proxy_read_timeout 70s;
    proxy_send_timeout 70s;
}
```

Требования к прокси: не резать кастомные заголовки провайдера, держать таймаут не
меньше `WriteTimeout` бота (65 секунд) и уметь достучаться до контейнера — либо общей
docker-сетью (`proxy_pass http://vpn-bot:8080`), либо пробросом порта на хост
(`ports: - "127.0.0.1:8080:8080"` и `proxy_pass http://172.17.0.1:8080`).
Полученный публичный адрес идёт в `PLATEGA_CALLBACK_URL` и в настройки вебхука ЮKassa.
Проверка после настройки: `/health` отвечает `OK`, а POST на callback без заголовков — `401`.

## Версии панели Remnawave

Бот одной сборкой работает и с панелью 2.8.x, и с 3.x. Версия определяется автоматически по
`GET /api/system/metadata`; если этот эндпоинт закрыт правами токена, бот определяет версию по
поведению панели. Настраивать ничего не нужно: смена версии подхватывается на лету (первый же
запрос с «неправильным» типом идентификатора приводит к перечитыванию версии) и, независимо от
активности пользователей, проверяется плановым проходом раз в 30 минут.

Различие между версиями одно, но принципиальное: в 3.x у пользователя панели больше нет UUID —
он адресуется числовым `id`. Поэтому бот хранит в таблице `users` оба идентификатора:
`remnawave_uuid` (заполнен у всех, кто создан на 2.8.x; допускает `NULL`) и `remnawave_id`
(есть в обеих версиях панели и переживает обновление без изменения значения).

### Порядок обновления панели до 3.x

Последовательность обязательная: обновление панели удаляет колонку `uuid` из её базы
безвозвратно, после чего сопоставить запись бота с пользователем панели по UUID уже нельзя.

1. Снять копию `bot.db` — миграция перестраивает таблицу `users` и необратима.
2. Выкатить актуальную версию бота, пока панель ещё 2.8.x.
3. Убедиться по логам (`make logs`), что заполнение `remnawave_id` прошло. Пользователей,
   которых панель не знает, бот перечислит в логе поимённо — их разбирают вручную.
4. Обновить панель до 3.x. Дополнительных переменных окружения релизная 3.x не требует.
5. Проверить по логам, что бот увидел новую версию панели, и пройти один сквозной сценарий:
   `👤 Моя подписка` → `📱 Мои устройства`.

Если панель обновили раньше бота — данные не теряются: новый бот при старте увидит 3.x и
восстановит `remnawave_id` поиском по Telegram ID (в фоне, не блокируя старт; до того как проход
дойдёт до конкретного пользователя, связка восстанавливается при первом обращении к нему).
Бесшовного отката панели с 3.x на 2.8.x не существует — только восстановление дампа Postgres.

Ошибки авторизации в панели (HTTP 401/403 — истёкший или отозванный токен, урезанные права)
бот не проглатывает молча: они логируются отдельной категорией и уходят сообщением владельцу.

### Подключение и ссылка подписки

Подключение целиком опирается на страницу подписки Remnawave: отдельного раздела инструкций в боте нет,
приложения и шаги настройки редактируются в панели и обновляются без релиза бота.

- Сразу после регистрации бот присылает два сообщения: приветствие с меню и отдельное сообщение с кнопкой
  подключения и ссылкой (Telegram не допускает reply- и inline-разметку в одном сообщении).
- Кнопки `🔗 Подключить устройство` и `🔄 Перевыпустить ссылку` показываются там же, где показывается сама
  ссылка: у активной и бессрочной подписки. В grace period и при исчерпанном трафике триала их нет.
- `📱 Мои устройства` доступны любому зарегистрированному пользователю.
- Перевыпуск сначала сбрасывает все HWID-устройства, затем меняет ссылку в панели. Если сброс не удался,
  ссылка остаётся прежней. Кнопки в старых сообщениях «Моя подписка» после перевыпуска ведут на нерабочую
  ссылку — раздел нужно открыть заново.

### Приглашения пользователей

Создавать новые ссылки могут пользователи с действующей оплаченной, перенесённой legacy-paid или бессрочной подпиской. Пробный пользователь и пользователь в grace period могут смотреть старые ссылки, но не создавать новые.

- Ссылка действует 30 суток, даёт приглашённому 72 часа trial и `TRIAL_TRAFFIC_LIMIT_GB` трафика.
- Цена берётся из `DEFAULT_SUBSCRIPTION_PRICE` и сохраняется в ссылке: будущая смена настройки её не изменяет.
- Одновременно разрешено 3 активных ссылки и не более 15 созданий за скользящие 24 часа.
- Активную ссылку можно в любой момент повторно отправить или мягко отозвать. История использованных ссылок сохраняется.
- После trial без оплаты доступ отключается, затем пользователь автоматически исключается существующим scheduler-flow.
- Первый пригласивший сохраняется навсегда для статистики, даже если пользователь позже вернулся по другой ссылке.
- Повторный trial после автокика пока сознательно разрешён; lifetime anti-abuse не входит в эту версию.
- Выплаты и новые начисления авторам приглашений отсутствуют.

## Поведение в граничных случаях

**Два вида инвайтов**:
- referral-инвайт пользователя (включая администратора в пользовательском режиме): 72-часовой trial, глобальная snapshot-цена, срок жизни ссылки 30 суток и учёт в рейтинге;
- служебный админский инвайт из `📋 Управление`: бессрочно (`2099-01-01`), без цены, трафик-лимита и referral-статистики.

**Срок подписки и продление**:
- продление через Platega добавляет 30 дней к текущему сроку (или от текущей даты, если уже истекло);
- раннее продление через Platega запрещено, если до истечения больше 90 дней;
- при сбое активации платёж остаётся подтверждённым, получает статус `confirmed_not_activated` и повторно обрабатывается scheduler без перезаписи исходного `confirmed_at`;
- администратор может перевести месячную подписку в бессрочную; при этом `invites.created_by` сохраняется, а `expire_days` становится `NULL`.

**Scheduler подписок**:
1. стартует с полным проходом при запуске бота и далее работает каждые 30 минут;
2. триал предупреждает менее чем за 24 часа и кикает сразу в точный `expireAt`;
3. оплаченную подписку предупреждает за 3 дня и менее чем за 24 часа;
4. в точный `expireAt` оплаченная подписка переводится в `DISABLED`, затем даётся 72 часа grace period;
5. после grace period пользователь удаляется, если свежая оплата не подтверждена;
6. в `maintenance mode` disable и автокики блокируются.
7. legacy-пользователи без инвайта и без `subscription_price` пропускаются новым payment-scheduler и продолжают жить по старой модели.
8. legacy-пользователь с уже оплаченным вручную текущим периодом может быть переведён на новую модель через `✏️ Изменить цену`:
   бот спросит, считать ли текущий период уже оплаченным; при ответе `Да` пользователь сразу пойдёт по paid-ветке с `💳 Продлить подписку`, напоминаниями за 3/1 день и grace period.

**Flow оплаты**:
1. пользователь выбирает `💳 Оплатить подписку` или `💳 Продлить подписку`;
2. бот показывает методы оплаты: `🏦 СБП`, `💳 Карта`, `🪙 Крипта`;
3. после создания платежа бот отправляет ссылку и кнопку `🔄 Проверить оплату`;
4. callback и ручная проверка синхронизируют локальный статус платежа (`confirmed`, `canceled`, `chargebacked`);
5. при успешной оплате подписка активируется автоматически, лимит трафика снимается;
6. если подтверждение получено, но Remnawave временно недоступен, пользователю не показывается ложное сообщение об активации: платёж остаётся в `confirmed_not_activated`, а scheduler повторяет активацию позже;
7. если оплата пришла по платежу, который бот успел локально закрыть (`expired`, `canceled`), она **принимается** — но только когда оплату подтверждает ответ API провайдера, сверенный с локальной записью, а не тело вебхука: подписка продлевается, чек пробивается, владелец получает уведомление о нештатной ситуации. Статусы `chargebacked` (деньги уже возвращены) и `confirmed_activation_failed` так не воскрешаются — по ним владельцу приходит алерт с просьбой разобрать операцию вручную. Молча проигнорированных подтверждений больше нет: провайдеру мы отвечаем успехом и повторной доставки не будет, поэтому о каждом таком случае бот сообщает владельцу один раз;
8. запросы к API ЮKassa повторяются до 3 раз (15 секунд на попытку, пауза между попытками растёт) при сетевых сбоях и ошибках 5xx; ошибки 4xx не повторяются. Повтор создания платежа безопасен за счёт ключа идемпотентности — касса возвращает тот же платёж, а не создаёт второй, и весь бюджет повторов укладывается в таймаут ответа вебхуку.

**Миграция старой moderator-модели**:
1. старые использованные moderator-инвайты становятся referral-историей, а `users.invited_by` заполняется первым автором;
2. старые неиспользованные referral-ссылки мягко отзываются, служебные админские ссылки остаются активными;
3. таблицы и поля модераторов/earnings сохраняются только как архив, новые начисления не создаются;
4. если у старого пользователя ещё нет `subscription_price`, админ задаёт цену через `✏️ Изменить цену`;
5. для legacy-case бот дополнительно спрашивает, был ли текущий период уже оплачен вручную;
6. ответ `✅ Да, считать оплаченной` помечает пользователя как migrated-paid без поддельного платежа в `payments`; ответ `❌ Нет, оставить trial` оставляет trial до первой оплаты;
7. вопрос показывается только для legacy-case с пустой ценой, активной finite-подпиской и отсутствием confirmed-платежей.

**Бан пользователя** — перманентная операция:

1. Telegram ID заносится в `banned_users`
2. Пользователь удаляется из Remnawave
3. Пользователь удаляется из БД бота
После бана пользователь блокируется на уровне `/start` и не может зарегистрироваться повторно.

**Автокик по истечению подписки** — это не бан. Пользователь может вернуться с новым инвайтом.

**Рассылка** — отправляется только пользователям со статусом `ACTIVE` в Remnawave. Пользователи с истёкшей подпиской или заблокированные не получают.

## Канал сообщества

Канал — форум-супергруппа с топиками (релизы, баги, идеи), привязанная к боту. Вход только по заявке: бот сам одобряет заявку **Платящего** пользователя и отклоняет остальных, объясняя отказ в личку.

### Включение

Фича активна, когда заданы **обе** переменные окружения; если не задана ни одна — бот работает ровно как раньше: обработчик заявок не регистрируется, упоминания Канала нигде не показываются.

Заданная половина настройки — почти наверняка опечатка, а молчаливое выключение владелец заметит нескоро (заявки просто повиснут неразобранными), поэтому такие случаи бот не прощает и **не стартует**:

- `COMMUNITY_CHAT_ID` задан, но не является числом — `invalid COMMUNITY_CHAT_ID`;
- задан `COMMUNITY_CHAT_ID` без `COMMUNITY_INVITE_LINK` — `COMMUNITY_INVITE_LINK is required when COMMUNITY_CHAT_ID is set`;
- задан `COMMUNITY_INVITE_LINK` без `COMMUNITY_CHAT_ID` — зеркальная ошибка;
- `COMMUNITY_CHAT_ID` положительный — потерянный при копировании минус: фича считалась бы включённой, но ни одна заявка не совпала бы с чужим ID;
- `COMMUNITY_INVITE_LINK` не является `http(s)`-ссылкой — Telegram отвергает сообщение с неподдерживаемой схемой в `href` целиком, то есть опечатка сломала бы кнопку `ℹ️ Информация` для всех.

| Переменная              | Описание                                                                       |
| ----------------------- | ------------------------------------------------------------------------------ |
| `COMMUNITY_CHAT_ID`     | Числовой ID супергруппы (обычно вида `-100…`)                                  |
| `COMMUNITY_INVITE_LINK` | Постоянная инвайт-ссылка с одобрением заявок администраторами                  |

Что нужно сделать владельцу руками:

1. Создать супергруппу, включить в ней топики (режим форума).
2. Добавить бота администратором с правами одобрять заявки на вступление и банить участников.
3. Создать постоянную инвайт-ссылку с опцией «одобрение заявок администраторами» и положить её в `COMMUNITY_INVITE_LINK`.
4. Указать ID супергруппы в `COMMUNITY_CHAT_ID` и перезапустить бота (`make up`).

Ссылку бот не создаёт и не ротирует, топиками и правами внутри супергруппы не управляет.

### Кто проходит гейт

Право на вход даёт предикат **Платящий** — тот же, что даёт право создавать referral-приглашения (расхождения между этими двумя местами быть не должно):

- пользователь не забанен и есть в базе бота;
- доступ действует: бессрочная подписка либо `ACTIVE`/`LIMITED` с неистёкшим сроком;
- и при этом есть подтверждённый платёж, либо стоит `legacy_paid_migrated`, либо доступ бессрочный.

Триал и grace period под определение не подпадают. Заявки триальщиков, пользователей в grace, автокикнутых, незнакомых боту и забаненных отклоняются. Объяснение «доступно с оплаченной подпиской — оплатите и подайте заявку по той же ссылке снова» уходит в личку всем, кроме забаненных: обещать путь внутрь тому, для кого вход закрыт навсегда, нечестно, поэтому заявка забаненного отклоняется молча. Telegram повторные заявки после отклонения не запрещает, поэтому они штатны, а объяснение дедуплицируется кулдауном 5 минут на пользователя (in-memory).

Владелец может добавить человека в Канал руками в обход гейта — бот состав не аудитит и списка участников не ведёт. Такой участник просто не получает приглашений: перед показом приписки бот спрашивает Telegram, состоит ли этот конкретный человек в Канале (см. «Как пользователи узнают о Канале»).

Если право проверить не удалось (Remnawave или база недоступны), заявка **не отклоняется**: сбой не должен выглядеть как решение по существу. Она остаётся висеть в Telegram, а владельцу уходит алерт (один на пользователя) — разобрать её нужно руками, потому что апдейт по заявке приходит один раз, а подать её заново Telegram не даёт. Ответ «пользователя нет в панели» (404) сбоем не считается: доступа нет, заявка отклоняется с объяснением как обычно.

### Выход из Канала

- **Перманентный бан** в боте выгоняет из Канала (ban+unban, без чёрного списка чата: вход и так закрыт гейтом). Кик идёт в фоне, его неудача бан не срывает. Выгоняет любой перманентный бан — и ручной бан админом, и автоматический бан по chargeback: мошенник не должен остаться в сообществе.
- **Прекращение оплаты, grace и автокик членства не лишают** — сообщество не должно терять людей из-за пауз в оплате.

### Как пользователи узнают о Канале

- `ℹ️ Информация` — упоминание со ссылкой видят все и всегда (при включённой фиче).
- Приписка внизу карточки `👤 Моя подписка`, сообщения об успешной оплате (по любому пути — и через callback провайдера, и через кнопку `🔄 Проверить оплату`) и ответа `📡 Серверы` — только Платящим, ещё не состоящим в Канале. Кулдаун общий на все места показа: 7 дней на пользователя, факт показа хранится в БД (таблица `community_members`) и переживает деплой.
- Пометка «в Канале» в БД гасит упоминания навсегда. Она ставится в двух случаях: бот одобрил заявку либо Telegram подтвердил членство при живой проверке. Выход из Канала пометку не снимает: человек уже в курсе.
- Перед показом приписки (последним шагом, уже после кулдауна) бот спрашивает Telegram `getChatMember`: вступившие по прямой ссылке владельца или до появления гейта иначе получали бы приглашение туда, где давно сидят. Ответ «внутри» гасит приписку навсегда. Если Telegram недоступен или бота разжаловали из админов, пользователь считается «снаружи» — бот скорее покажет лишний абзац раз в неделю, чем замолчит незаметно.
- Пользователи, не проходящие предикат, приписок не видят вообще (кроме `ℹ️ Информация`) — бот не дразнит недоступным.

## Чеки «Мой налог»

Бот сам пробивает чеки самозанятого в кабинете «Мой налог» (`lknpd.nalog.ru`) по каждому подтверждённому платежу ЮKassa — вручную заходить в приложение ФНС не нужно.

### Включение

Интеграция включается наличием `MOYNALOG_INN` и `MOYNALOG_PASSWORD` — так же, как Platega и ЮKassa. Если они не заданы, бот работает как раньше: чеки не пробиваются, никакие запросы к ФНС не идут.

| Переменная              | Описание                                                                  |
| ----------------------- | ------------------------------------------------------------------------- |
| `MOYNALOG_INN`          | ИНН самозанятого                                                          |
| `MOYNALOG_PASSWORD`     | Пароль от кабинета «Мой налог»                                            |
| `MOYNALOG_SERVICE_NAME` | Базовая часть наименования услуги (дефолт: `Sarvizza - Подписка на месяц`) |

Токен авторизации живёт только в памяти процесса и на диск не пишется. Идентификатор устройства вычисляется детерминированно из ИНН, поэтому перезапуски бота не плодят новые устройства в кабинете.

### Как это работает

- Чек пробивается сразу после активации подписки, но в отдельной горутине — вне ответа вебхуку платёжного провайдера. Недоступность ФНС никогда не задерживает ответ провайдеру и не оставляет клиента без оплаченной услуги.
- Сумма чека — **полная** сумма платежа: комиссия провайдера налоговую базу при НПД не уменьшает. Покупатель — физлицо, без имени и телефона.
- Наименование услуги — база из `MOYNALOG_SERVICE_NAME` плюс случайная метка из 6 символов в скобках. Метка нужна для сверки (см. ниже).
- Связь чека с платежом строго 1:1 (ключ `payment_id` в таблице `receipts`), а право на пробитие столбится до обращения к ФНС. Двойной чек по одному платежу невозможен физически, даже если платёжный путь и плановый проход сработают одновременно.
- Плановый 30-минутный проход scheduler добивает недоделанное: подтверждённые платежи ЮKassa без чека и чеки в состояниях `pending`/`unknown`. Повторы бесконечные, сбой этого шага не срывает остальные шаги прохода. Шаг идёт **последним** и с бюджетом в 5 минут: поход в ФНС долгий, а уведомления, отключения и автокики ждать его не должны — что не успели, добирается следующим проходом.
- **Сверка по метке.** Если ответ ФНС потерялся (состояние `unknown`), бот ищет свой чек в списке доходов за сутки вокруг времени операции по вхождению метки: одно совпадение — записывает uuid, ноль — пробивает заново, больше одного — состояние не меняет и шлёт владельцу алерт.
- **Отвергнутый чек (состояние `rejected`).** Если ФНС ответила «неверный запрос» (HTTP 400/403/404), повторять бесполезно: чек уходит в терминальное состояние, плановый проход его больше не берёт, а владелец получает сообщение с текстом от ФНС — разбирать нужно руками в кабинете.
- **Ошибка входа останавливает весь проход по чекам** до следующего раза: пароль не относится к конкретному платежу, и перебор очереди означал бы десятки неудачных входов подряд — риск блокировки кабинета. После исправления пароля следующий проход работает как обычно.
- Тестовые платежи админа пробиваются наравне с обычными.
- Аннулирование чека при возврате средств пока не автоматизировано — возвраты оформляются в кабинете вручную.

### Платежи Platega в «Мой налог» не вносятся

Это **осознанное решение владельца**, а не упущение: чеки по платежам Platega не создаются и в кабинет не попадают, бот пропускает их молча, без ошибок и предупреждений.

### Оповещения

Разделены по типу проблемы, чтобы не превращаться в шум:

- ошибка авторизации и «неверный запрос» (HTTP 400/403/404) — сообщение владельцу сразу, с текстом от ФНС;
- недоступность ФНС и транспортные ошибки — молча, они лечатся повторами;
- чек не пробит больше суток — сообщение с платежом, датой и текстом последней ошибки;
- сводка раз в сутки, пока есть непробитые чеки;
- когда непробитых чеков нет — сообщений нет вообще.

Сообщения об отвергнутых и застрявших чеках помечаются в базе, а не в памяти процесса, — они не повторятся после перезапуска бота, но и не потеряются. Оплата (в том числе тестовая оплата самого владельца) эту память больше не сбрасывает: сброс уведомлений при новом платеже маркеры чеков не трогает.

Если интеграция выключена, а подтверждённые платежи без чеков в базе есть, бот пишет WARN в лог и один раз сообщает об этом владельцу.

### Обязательные явные DNS

В `docker-compose.yml` контейнеру бота **обязательно** заданы явные DNS (`8.8.8.8` и `77.88.8.8`). Провайдерский резолвер Hetzner (`185.12.64.1`/`185.12.64.2`) и Cloudflare отдают SERVFAIL на `lknpd.nalog.ru`, тогда как Google, Quad9, OpenDNS, AdGuard и Яндекс резолвят его нормально (`213.24.64.181`). Без этой настройки интеграция просто не заработает, а симптом будет выглядеть как отказ ФНС — не тратьте время на отладку клиента, проверьте резолвинг.

## Мониторинг нод

Бот мониторит VPS-ноды через Prometheus Node Exporter и отображает их состояние в live-дашборде (кнопка `📡 Серверы`). При уходе ноды в офлайн или перегрузке приходит алерт в Telegram.

### Настройка

На каждой ноде выполни:

```bash
bash <(wget -qO- https://raw.githubusercontent.com/fUS1ONd/vpn_bot/main/scripts/install-node-exporter.sh) <IP_СЕРВЕРА_С_БОТОМ>
```

Скрипт устанавливает Node Exporter, открывает порт 9100 только для IP сервера с ботом и добавляет сервис в автозапуск.

В Remnawave добавь тег `bw:<Mbps>` к ноде для указания bandwidth (например `bw:1000` = 1 Gbit). По умолчанию 1000 Mbps.

### Алерты

- Нода **OFFLINE** — Node Exporter не отвечает
- **Load Index > 80%** — нода перегружена (`Load Average × 100 / bandwidth`)
